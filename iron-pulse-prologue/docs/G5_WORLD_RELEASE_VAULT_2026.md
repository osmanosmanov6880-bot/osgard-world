## 1. Реальный результат, а не обещание облачной платформы

Новый `ci/release_vault_g5.py` собирает один проверяемый архив из **фактически экспортированной игры Windows x64, Godot WebGL, международного веб-портала и исходных SHA-доказательств**. Не создаёт мультяшные изображения, не генерирует фальшивые показатели FPS и не подменяет игровой движок HTML-макетом.

Полная проверка выполняется после настоящих нативных V1–V18/G1–G4, Chromium WebGL и портала RU/EN. После подтверждения кода CI создаёт:
- `build/g5-release/IRON_PULSE_WORLD_G5_RELEASE_HOLD.zip` — пакеты `site/`, `windows/`, `proof/` и `meta/release-manifest.json`;
- `build/g5-release/RELEASE_RECEIPT.json` — размер и SHA-256 целого архива, точный исходный Git-коммит, явный `release_hold=true`;
- `build/g5-release/PINNED_SHA256SUMS.txt` — внешний контрольный SHA-256 для сверки;
- `build/proof/G5_STAGE_RELEASE_HOLD.txt` — констатация успешного непроизводственного staging.

В архив включены только явно разрешённые ресурсы (портал, настоящий WebAssembly/PCK/JS runtime, пользовательские изображения, Godot Windows EXE+PCK, исходные доказательства). Исходные `.import`-файлы и произвольные дополнения не попадают в релиз. Каждая запись имеет размер и SHA-256; весь архив тоже имеет внешний SHA-256. Записи ZIP с `../`, абсолютными путями, дубликатами, конфликтами регистра, ссылками и незаявленными файлами блокируются.

**Граница доверия:** SHA-256 позволяет обнаружить несоответствие *уже доверенному* хэшу/манифесту. Он **не доказывает авторство** без отдельной цифровой подписи и защищённого канала доставки. Windows EXE не заявляется подписанным. Даже идеальный CI не означает, что приложение проверено на реальном Windows/Android/iPhone.

## 2. Проверяемый локальный staging, управление версиями и откат

Ниже команды для оператора. Пути условные: использовать настоящий ZIP и **хэш из доверенного CI**, а не вычислять контрольный хэш уже подозрительного файла.

```bash
# 1. Сверить точный Git-коммит и внешний SHA-256
python3 ci/release_vault_g5.py verify \
  --archive /verified/IRON_PULSE_WORLD_G5_RELEASE_HOLD.zip \
  --source-sha <TRUSTED_40_HEX_GIT_SHA> \
  --bundle-sha256 <TRUSTED_64_HEX_ARTIFACT_SHA>

# 2. Без установки игры и без производства положить в версионированное хранилище
python3 ci/release_vault_g5.py stage \
  --archive /verified/IRON_PULSE_WORLD_G5_RELEASE_HOLD.zip \
  --vault /offline/iron-pulse-vault \
  --source-sha <TRUSTED_40_HEX_GIT_SHA> \
  --bundle-sha256 <TRUSTED_64_HEX_ARTIFACT_SHA>

# 3. Посмотреть текущий локальный указатель; по умолчанию он отсутствует
python3 ci/release_vault_g5.py status --vault /offline/iron-pulse-vault

# 4. Только по отдельному решению оператора: поменять ЛОКАЛЬНЫЙ УКАЗАТЕЛЬ
python3 ci/release_vault_g5.py activate \
  --vault /offline/iron-pulse-vault \
  --source-sha <TRUSTED_40_HEX_GIT_SHA> \
  --expected-current none

# 5. Когда появится предыдущая проверенная версия, ручной откат указателя
python3 ci/release_vault_g5.py rollback \
  --vault /offline/iron-pulse-vault \
  --expected-current <CURRENT_40_HEX_GIT_SHA>
```

Указатель защищён проверкой ожидаемого текущего SHA (compare-and-swap), записывается через атомарную замену файла и не заменяет бинарные файлы предыдущих версий. Восстановление отказывается работать, если прежняя стадия нарушена. `activate`/**`rollback` только изменяют локальный файл `state/current.json`**, НЕ деплоят сайт, НЕ переключают реальные домены/CDN и НЕ дают разрешения на production.

## 3. Проверки безопасности и воспроизводимости

`ci/test_release_vault_g5.py` независимо выполняет 5 сценариев:
1. Две сборки с одинаковыми входами совпадают побайтно; релизный манифест и внешний SHA корректны.
2. Два независимо staged тестовых выпуска переключаются с проверкой ожидаемого состояния, откатываются и не затрагивают предыдущие файлы. Повреждение staged-бинарника блокирует дальнейшие операции.
3. Подмена хэша, повреждение ZIP, ZIP-slip `../`, конфликтующие имена, неизвестный JavaScript, символическая ссылка и дубликаты блокируются.
4. Заменённый Windows EXE с несовпадающим доказательством CI отвергается; stage требует заранее закреплённый внешний SHA.
5. Подпись, физическая сертификация и production-ready никогда не выставляются автоматически.

Файлы в этих тестах **синтетические**, специально небольшие и явно не называются настоящими игровыми бинарниками. **Отдельная обязательная CI-операция** упаковывает уже реальные экспортированные Godot файлы, сверяет их и staging, а затем проверяет, что `state/current.json` отсутствует: CI не может самостоятельно активировать релиз.
