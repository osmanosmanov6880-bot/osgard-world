## W83.7 — ROOT CAUSE: CDP real changed-touch semantics (browser driver)
The long W83 browser failure sequence up to [run #40769635075](https://github.com/osmanosmanov6880-bot/osgard-world/actions/runs/40769635075) had an actual **test-driver protocol error**. The driver used `touchStart([a,b])` and `touchMove([a,b])` while a was already active, then `touchEnd([a])` to "release camera b". Under the **actual Chromium default implementation** of `Input.dispatchTouchEvent`, the passed touch-point list represents the *changed* points: `touchEnd([a])` really ends walking finger a, while finger b stays active. This is why W70 active walk fell to zero and one real walk touch-end was reported, regardless of timer fixes. A documented Chromium browser automation issue (2026-10-05, https://issues.chromium.org/issues/569778218 ) explicitly verifies `touchEnd([point])` releases *that point only*, while the published CDP wording conflicts with its default implementation. W83.7 now sends **only** `touchStart([b])`, `touchMove([b])`, `touchEnd([b])`, and only AFTER proving walking remains active, `touchEnd([a])`. The test attaches a **passive, capture-only DOM TouchEvent audit** to the real Godot canvas, records `changedTouches` and `touches`, and fails if b does not end while a remains or if the final end doesn't release a. All original W70/physics, mission and scoreboard unchanged; no fake camera/body or JS game state mutation. The driver still strictly requires actual W70 held-key + original collision movement + 18 SHA-verified live frames. Source-based iPhone/Android hardware remains HOLD.
