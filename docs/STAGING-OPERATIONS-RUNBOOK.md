# OSGARD staging operations — четыре новых независимых модуля

Новая ветка добавляет автономные инструменты для ручного и CI-аудита процесса выпуска.

1. `scripts/staging-http-acceptance.py`: ограниченные GET проверки шести HTML-маршрутов на заранее выбранном HTTPS staging origin, запрет перехода на чужой origin. Не подключать к реальному сайту без согласованного staging URL.
2. `scripts/rollback-readiness.py`: проверка доказательств доступности предыдущего релиза, контрольной суммы резервной копии, факта испытания восстановления, назначенного оператора и окна обслуживания. Никогда не производит rollback самостоятельно.
3. `scripts/release-config-audit.py`: минимальные обязательные файлы, security headers и подозрительные ключи по названиям в собранном артефакте. Это не полноценное сканирование секретов или аудит CSP.
4. `scripts/release-matrix.py`: семь обязательных оценок готовности и сохранение состояния только `ready_for_review` при отсутствии ручного разрешения.

## Примеры
```sh
python3 scripts/staging-http-acceptance.py --origin https://staging.example.com
python3 scripts/rollback-readiness.py /private/rollback-evidence.json
python3 scripts/release-config-audit.py dist
python3 scripts/release-matrix.py /private/release-matrix.json
python3 -m unittest discover -s tests -p test_staging_operations.py -v
```

Эти утилиты не выполняют публикацию, оплату, импорт или изменение базы данных. Единая матрица принимает статусы как **непроверенные утверждения**, поэтому её нельзя использовать вместо независимых доказательств GitHub API и проверки артефакта. HTTP checker делает лишь простую проверку маршрутов; не проверяет логин, выполнение JS, безопасность и доступность игр.

Открытые зависимости: настоящий staging URL, production-like Core service без реальных клиентских данных, испытание восстановления и проверка отката с авторизованным оператором. До этого `ready_for_review` не означает `released`.

## Защита сетевых проверок (hardening)

HTTP-клиент staging теперь отказывает при HTTP-перенаправлении до попытки обращения по адресу из `Location`. Литералы приватных, локальных и зарезервированных IP-адресов запрещены. Это **не полная защита от DNS rebinding**: staging-проверки должны запускаться в изолированном CI/хосте с egress-ограничениями для приватных подсетей. Не направляйте её на production. Новые отрицательные тесты проверяют редиректы и приватные адреса.

## Привязка проверенного каталога к ZIP

`scripts/staging-release-acceptance.py` принимает один согласованный комплект: каталог `--dist`, архив `--zip` и его `--manifest`. Проверка сравнивает полный список файлов, размеры и SHA-256 каталога с манифестом, который независимо сверяется с содержимым ZIP. Контрольная сумма канонического манифеста должна совпадать у обеих проверок.

Чистый посторонний каталог не может подтвердить настройки архива с отсутствующими security headers. Изменение, удаление или добавление файлов в `dist` после упаковки также блокирует допуск. После любых изменений нужно заново собрать весь комплект; для выходных файлов сборщик требует новые пути. При ошибке соответствия команда завершает работу с ненулевым кодом; при успешной проверке результат содержит `checks.dist_manifest=verified` и заявленный `commit_sha`.

`verify-zip-manifest.py` требует строковый Git SHA из 40 или 64 шестнадцатеричных символов, целочисленные `schema_version=1` и `file_count`. Это проверка формата и согласованности декларации: существование коммита и соответствие исходников артефакту по-прежнему подтверждаются доверенной сборкой и свидетельствами CI. `release-config-audit.py` одинаково обрабатывает пробелы и табуляцию перед заголовками глобального правила `/*`.

```sh
python3 scripts/staging-release-acceptance.py --dist dist --zip /tmp/osgard-release/site.zip --manifest /tmp/osgard-release/manifest.json
python3 -m unittest discover -s tests -p test_staging_release_acceptance.py -v
python3 -m unittest discover -s tests -p test_zip_manifest_binding.py -v
```

Регрессии используют настоящие временные ZIP, манифесты и каталоги с 19 игровыми входами. Они проверяют подмену каталога, изменение файлов после упаковки, неверный Git SHA и табуляцию в `_headers`. Статус `ready_for_staging_review` подтверждает только перечисленные статические проверки; запуск игры в браузере, staging deployment и восстановление Core остаются отдельными этапами.
