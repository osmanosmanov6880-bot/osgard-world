## Гарантия и границы

Защищённым считается только новый матч, для которого сервер атомарно записал владельца, назначенного игрока и подтверждённую попытку создания, прежде чем вернуть `201`. Источник личности — реальная непросроченная сессия Core через `/api/core/auth/me`. `playerId`, `creatorId`, идентификатор в URL и данные браузерного хранилища сами по себе не подтверждают личность.

Владение распространяется на чтение состояния, результата и отправку команд — как через `/v2`, так и через старые `/v1/matches/:id/...` адреса. Зафиксированный результат также требует действующей сессии владельца. Иной аккаунт получает `403`, отсутствующая/неверная сессия — `401`, недоступный Core — `503` без отправки защищённой команды.

Это один авторизованный участник в существующем legacy-матче вместимостью два игрока. Здесь не реализованы безопасное присоединение второго участника, закрытый ACL испытаний, восстановление симулятора после потери его активного состояния, проверенный повтор или атомарное завершение матча. Проверка фазы и отправка команды остаются двумя операциями legacy API.

## Контракт v2

Все пути относительны `/api/remix`. Bearer передаётся только по фиксированному same-origin адресу, а не на пользовательский URL игрового сервиса.

| Метод и путь | Результат |
| --- | --- |
| `GET /v2/capabilities` | Версия политики, возможность создания, провайдер и точные границы |
| `POST /v2/matches` | Core bearer + `Idempotency-Key`; новый защищённый матч после durable binding |
| `GET /v2/matches?after=:id` | Только матчи текущего аккаунта, максимум 50; `nextCursor` для следующей страницы |
| `GET /v2/creation-attempts/:key` | Состояние конкретной попытки текущего аккаунта без повторного POST |
| `GET /v2/matches/:id` | Подтверждённые метаданные и максимальная отправленная последовательность |
| `GET/HEAD /v2/matches/:id/state` | Прежний проверяемый DTO состояния после проверки владельца |
| `GET/HEAD /v2/matches/:id/result` | Прежний DTO результата; terminal snapshot не заменяет проверку владельца |
| `POST /v2/matches/:id/input` | Проверка владельца, фазы, игрока и последовательности; одна отправка |

Создание принимает ровно `{"challengeId":"…","maxPlayers":2}`. Ответ содержит `id`, `challengeId`, `maxPlayers`, `createdAt`, `playerId`, `highestSubmittedSequence`, `accessMode:"core-owned"`. Назначенный `playerId` имеет случайный суффикс и не выбирается браузером.

Команда принимает `sequence`, `moveX`, `moveY`, `jump`; необязательный `playerId` должен совпасть с серверным. Число `highestSubmittedSequence` означает максимальный **отправленный**, включая неподтверждённые команды, номер. Оно не называется последним принятым номером. Новый номер резервируется в SQLite до upstream POST; повторный и меньший номер блокируются после перезапуска тоже.

## Неоднозначный результат создания

Перед upstream POST записывается попытка с хэшем запроса. Повтор завершённой попытки возвращает уже связанный матч; другой payload с тем же ключом получает `409`. Потерянный ответ, обрыв процесса или невозможность подтвердить binding оставляют попытку неопределённой. Автоматического повторного POST и присвоения старого матча по его ID нет.

Legacy API не поддерживает ключ операции или поиск созданного объекта по нему. Если процесс погиб после создания, но до получения ID/записи binding, в симуляторе может остаться пустой несвязанный объект. До binding upstream получает только публичные `challengeId` и `maxPlayers`; туда не передаются аккаунт, назначенный игрок, bearer или cookie. Такой объект не возвращается как защищённый матч, не присваивается аккаунту при повторе и не содержит отправленных владельцем команд. Неопределённая попытка не блокирует все посторонние гостевые матчи.

Во время живого создания общий эксклюзивный файловый lock закрывает окно между legacy POST и binding. Остальные операции матча удерживают общий lock от классификации доступа до окончания запроса. Отдельные файловые полосы сериализуют операции одного матча и работают между процессами. Ожидание ограничено общим deadline; файловые пути не получаются из пользовательского ввода.

## Хранилище, токены и откат

Terminal state/result сохраняют прежний формат и сериализованные байты. Добавлены таблицы владельцев, попыток создания и известных гостевых матчей. Основа понимает `user_version` 1 и 2. Первая защищённая резервация атомарно поднимает версию до 2; версия никогда не понижается. Старый guard с поддержкой только версии 1 откажется запускаться на таком хранилище.

Если у уже мигрировавшей базы версии 2 отсутствует обязательная таблица или нарушена форма столбцов, запуск прекращается. Сервер не восстанавливает пустую таблицу владельцев поверх повреждения: такое восстановление сделало бы прежний защищённый результат гостевым. Независимая проверка воспроизвела исходную ошибку, после исправления проверены отказ текущего процесса и отказ после перезапуска без изменения версии базы.

Самого отказа старого бинарного файла недостаточно для рабочего отката. Скрипт развёртывания при включении создания заранее требует:

1. Текущий рабочий guard сообщает `authPolicyVersion:1` и `ownershipPolicy:"confirmed-durable-binding"` и станет точным контейнером отката.
2. У Legacy API нет опубликованных портов, включая loopback; текущие и настроенные привязки проверяются отдельно. Docker Engine должен иметь распознанную стабильную версию не ниже 28. Каждая фактически подключённая сеть проверяется по точному ID: только локальная пользовательская bridge-сеть в NAT-режиме, без trusted host interfaces и нестандартного masquerading. Прямые routed/macvlan/ipvlan, общие host/container и неизвестные варианты отклоняются.
3. Проверка выполняется до остановки Core или guard. Активация останавливает старый guard перед запуском нового и сохраняет тот же именованный том.

При выключенном создании права на существующие матчи продолжают действовать. Сбой Core не превращает их в гостевые; обычные гостевые операции продолжают работать без Core. Внутренняя проверка идёт к `http://core-api:4173` с фиксированным `Host: osgard.world`, без положительного кэша сессий. Bearer/cookie не отправляются legacy API, не сохраняются в SQLite и не попадают в сообщения об ошибках.

Проверка сетевых метаданных опирается на штатную фильтрацию Docker, описанную в [документации публикации портов](https://docs.docker.com/engine/network/port-publishing/) и [изменениях Engine 28](https://docs.docker.com/engine/release-notes/28/). Она не подтверждает произвольные изменения firewall хоста или отключение его правил оператором. Секреты, переменные окружения и исходники частного legacy-сервиса при этой проверке не читаются и не экспортируются.

## Клиент, восстановление и публичная проверка второго этапа

Этот раздел описывает опубликованный клиент PR #135. Замороженный [HTML с контроллером сессии](../public/games/remix/index.html) имеет SHA-256 `354e52e87faa6e5be4a1db35b8c2f29227faf82ed8bbeb0f4b888007202b0a1d`; [слой RU/EN](../public/games/remix/interface.js) содержит соответствующие действия и сообщения об ограничениях. Точные опубликованные исходники и реальный API проверены отдельно от browser fixtures, как описано выше.

Режим «Матчи аккаунта» выбирается отдельно от гостевого. Он читает текущий Core-токен из `sessionStorage` по ключу `osgard:core-session:v1`, подтверждает личность через `/api/core/auth/me` и использует только `/api/remix/v2/` того же origin. Пользовательский API URL не получает bearer; cookies не прикладываются, HTTP-перенаправления отклоняются. Смена токена или аккаунта останавливает защищённый ввод и очищает показ прежнего результата/истории. Сохранённые записи другого аккаунта остаются у него; гостевые матчи не присваиваются аккаунту и защищённые запросы не переключаются на гостевой протокол при ошибке.

До POST клиент сохраняет отдельные неизменяемые записи: для создания — исходное испытание, область ссылки и ключ операции; для ввода — матч и зарезервированный номер команды. Основная запись выбранного матча может устареть при работе двух вкладок и не является единственным источником восстановления. Журналы разделены по API и подтверждённому аккаунту; ввод привязан к самому матчу, поэтому другая ссылка не обнуляет использованные номера. Неопределённое создание обнаруживается и после смены ссылки или даты. Восстановление запрашивает GET попытки/метаданных; потерянный POST не воспроизводится. Игрок приходит с сервера, а следующий номер выше максимума серверного `highestSubmittedSequence` и сохранившихся локальных резервов.

Очистка следует подтверждению сервиса. Запись создания удаляется после подтверждённого отказа либо после `ready` и успешного сохранения активного матча. `uncertain`, потеря ответа и `404` попытки её не удаляют. Резервы ввода удаляются только для соответствующего матча и до номера, подтверждённого ACK либо серверными метаданными; записи другого матча/аккаунта не затрагиваются. Ошибка чтения, перечисления или записи хранилища, повреждённая запись и достижение локального порога 32 записей в журнале приостанавливают создание матчей и отправку новых команд. Неопределённые записи не выбрасываются ради освобождения места.

`localStorage` не предоставляет общей транзакции или compare-and-swap между вкладками. Журналы защищают восстановление от устаревшего указателя, но не доказывают атомарный выбор номера или единственный одновременный запуск во всех вкладках. Конфликты номеров и ключей окончательно разрешает серверный контракт. Это также не обещание сохранности после удаления данных браузера, восстановления утраченной активной симуляции или проверки повторов.

Только подтверждённый серверный отказ создания при доступной возможности создания открывает отдельное действие «Создать новое публичное испытание». Оно создаёт одно публичное испытание без Core-bearer и новую попытку owned-матча с новым сохранённым ключом. Неопределённый ответ и ошибка браузерного хранилища не разрешают такой обход; публичность испытания не означает право другого аккаунта присоединиться к защищённому матчу.

[Публичная CLI-проверка](../scripts/remix-owned-live-smoke.py) по умолчанию выполняет только чтение. Явный `--exercise-owned` предусмотрен для одного запуска после публикации: два отдельных QA-аккаунта, одно QA-испытание с `visibility:private` и один owned-матч. Credentials остаются в памяти, попытки запросов учитываются до отправки, неопределённые POST не повторяются. Для каждого известного токена допускается одна попытка logout; неизвестный результат auth или неподтверждённый logout исключает `allQaSessionsLoggedOut:true`. Отчёт очищен от credentials, а `resultSha256` обозначает хэш результата, не проверенный replay.

Первая попытка выполнить CLI через прямой `http.client` завершилась `gaierror` на первом GET, до создания аккаунтов и всех POST; её [отчёт](evidence/remix-owned-transport-failure-2026-10-17.json) не изменён. Для сети этой среды добавлен отдельный [QA-запускатель](../scripts/with-remix-runtime-proxy.py): он использует stdlib `getproxies()`/`proxy_bypass()`, только HTTP CONNECT к фиксированному `osgard.world:443`, исходный HTTPSConnection с проверкой сертификата/имени сайта и proxy-authorization только в CONNECT. Исходный probe не изменён, его SHA-256 — `e816b676d3bf32280adb54f1efa59404c4ab0c557a71c86da6b434c5812bb79d`. Аргументы, журнал, SIGALRM/deadline и очистка остались исходными; переходы, fallback и POST-retry не добавлены. Независимый review и 20 автономных тестов предшествовали единственному успешному запуску с созданием QA-аккаунтов.
