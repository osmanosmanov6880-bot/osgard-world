# NULL SHIFT, REMIX и восстановление Core: локальная приёмка

Дата: 17 октября 2026 года. Этот документ описывает следующий блок после `GAMES-RELIABILITY-2026-10-17.md`. Предыдущая матрица с четырьмя блокировками остаётся историческим результатом того кандидата.

## Область работы

Основная игра NULL SHIFT должна проверяться после настоящего Godot Web export. REMIX должен принимать ввод через реальный HTTP-сервис и выдавать вычисленный сервером результат. Восстановление Core должно проходить через отдельный процесс приложения и реальные API-операции, включая данные, которые ещё находятся в SQLite WAL.

Локальная приёмка не публикует сайт и не меняет рабочую базу. Внешний REMIX/Unity backend, указанный в production compose как `../remix/backend`, отсутствует в доступных исходниках. Новая арена включается отдельным флагом `--remix`; production proxy и конфигурация внешнего сервиса сохраняют свой существующий маршрут. Это явно объявленный `remix-arena-v1`, а не подтверждение совместимости с недоступным сервером Unity.

## Единая сборка Godot

`scripts/build-null-shift-godot.py` использует официальный Godot `4.7.2.stable.official.ed1daf0bf` и однопоточный release Web template. Версия, размеры, SHA-256 архивов и извлечённых файлов закреплены в `godot/toolchain-lock.json`. Источник — [официальный выпуск Godot 4.7.2](https://github.com/godotengine/godot-builds/releases/tag/4.7.2-stable).

Перед каждым использованием проверяется содержимое кеша. Повреждённый исполняемый файл восстанавливается только из архива, прошедшего проверку размера и SHA-256. Полный архив шаблонов скачивается при первой установке; в CI кешируются только необходимые движок и Web template. Сборщик рассчитан на Linux x86_64 и Python 3.11+; CI использует Python 3.12.

Экспорт выполняется после импорта проекта и полного штатного native runtime smoke. Ненулевой exit code, ошибки GDScript, превышение времени или отсутствие завершающего PASS останавливают сборку. Временный экспорт проверяется до замены предыдущего локального результата.

Каждый native runtime smoke получает новые временные XDG data/config/cache каталоги. Проверка действительно сохраняет карьеру и покупает улучшение, поэтому общее `user://` между сборками переносило бы оружие и кредиты в следующий запуск. Изоляция сохраняет исходные условия и не удаляет существующие пользовательские сохранения.

`build-info.json` связывает:

- версию движка и SHA-256 файла закреплённого toolchain;
- хеш всех исходных файлов Godot, включая `.gd.uid`, без каталога `.godot`;
- точные имена, размеры и SHA-256 сгенерированных файлов;
- успешное завершение native runtime smoke.

Проверка после `npm run build` подтверждает, что в `dist` попал тот же экспорт. Изменение исходника, подмена JavaScript/WASM/PCK, добавленный или отсутствующий файл и другой toolchain блокируют приёмку. Метаданные экспорта входят в общий manifest и ZIP, которые отдельно привязаны к Git SHA.

### Обычный браузер и Pages-пакет

Для обычного локального сервера используется несжатый `index.wasm`. Для Cloudflare Pages существующий лимит 25 MiB на файл сохраняется: `compress-pages-wasm.mjs` упаковывает WASM в gzip и проверяет побайтовое восстановление. Метаданные обновляются для фактических сжатых байтов и содержат хеш исходного WASM.

Упакованный файл требует `Content-Encoding: gzip` и `Content-Type: application/wasm`. Флаг `--cloudflare-headers` локальной приёмки проверяет точное правило в `_headers` и включает этот заголовок только для Godot WASM. Он не создаёт ответы игровых API. Полный browser matrix запускается на этих файлах до формирования ZIP.

Обычный Vite preview не интерпретирует правила Cloudflare `_headers`. Для обычного preview используйте несжатую сборку; упакованную сборку проверяйте с её объявленным профилем доставки.

### Исправления, обнаруженные исполнением Godot

Первый настоящий Web-запуск выявил ошибки, которые не обнаруживались проверкой наличия файлов:

- На телефоне с шириной 390 CSS px движок сохранял внутреннюю раскладку 1600×900. Сенсорные кнопки сжимались примерно до 9 px. Shell теперь задаёт реальный прямоугольник canvas с отступом под шапку и размером backing buffer по DPR; Godot строит интерфейс в фактических CSS px. Основные сенсорные цели имеют размер не меньше 44×44 px, а модальные окна ограничены шириной экрана.
- Луч оружия проходил выше коллайдеров обычных противников. Высота физического выстрела теперь совпадает с высотой видимого оружия. Приёмка требует уменьшения настоящих HP охраны после mouse/touch fire.
- Экспортный шрифт не показывал стрелки управления. Четыре локальные SVG-иконки сохраняют читаемые направления движения и шифра без внешнего шрифта.
- Компактный интерфейс скрывал кнопку паузы, а кнопки меню не принимали фокус с клавиатуры. Добавлены мобильная пауза, видимый фокус, Enter для продолжения и Tab/Enter для перезапуска.
- Одно касание мобильной паузы порождало повторную фазу нажатия и повторно переключало игру. Действие теперь явно устанавливает паузу. Пауза останавливает время рейда, опасности, движение, урон и перезарядку; удержанный ввод сбрасывается при паузе и потере фокуса.
- Мобильный HUD оказывался выше заданных 130 px из-за минимальной высоты текста, а следующая панель оставалась на фиксированной координате и закрывала строку рывка. Следующая панель теперь располагается на 8 px ниже фактической высоты HUD. Нативный smoke измеряет настоящие границы обеих панелей и строки после изменения размера окна.

Новый `browser_probe.gd` включается только с `?test=1` и выдаёт свежий неизменяемый снимок нативной сцены. Он не предоставляет команд движения, телепортации, урона, сохранения или победы. Браузерный сценарий управляет игрой через настоящие клавиши, мышь и touch, а через probe только проверяет последствия. Полное прохождение миссии и испытания на физических телефонах остаются отдельными проверками.

## REMIX: серверная арена

`server/remix_service.py` реализует версионированную пошаговую арену 12×7. Каждый заезд принадлежит одному аутентифицированному пользователю Core. Публичное испытание можно проходить отдельными заездами и сравнивать лучшие результаты разных игроков. Capability `playersPerMatch: 1` явно исключает обещание синхронного мультиплеера.

Сервер проверяет seed, геометрию, единственную цель, доступный безопасный путь, типы полей и лимиты. Ввод содержит направление, намерение прыжка и последовательный номер. Позиция, столкновения, штрафы, завершение и счёт вычисляются сервером. Время результата — стоимость шагов и штрафов согласно правилам арены; скорость отправки HTTP-запросов не улучшает результат.

Полный цикл:

1. Автор создаёт личный draft через Core bearer session.
2. Автор проходит проверочный заезд настоящими вводами.
3. Сервер повторно вычисляет журнал; только успешный proof разрешает validate/publish.
4. Другой аккаунт получает опубликованную арену и начинает собственный заезд.
5. Результат и replay содержат seed, версию правил, назначение заезда, упорядоченный ввод, контрольные состояния и хеш.
6. Лучший заезд каждого игрока попадает в таблицу результатов; выбранные повторы проверяются перед выдачей.
7. REMIX опубликованного испытания создаёт новый draft с сохранённой ссылкой на родителя и новым автором.

Идентификатор автора/игрока берётся из действующей Core-сессии. Чужие draft и заезды недоступны; отозванный токен не разрешает запись. Повтор одного запроса с тем же ключом и повтор того же номера ввода не создают дополнительный ход. Изменённый запрос с прежним ключом и нарушение последовательности возвращают конфликт.

При чтении результата проверяется весь сохранённый ответ, включая идентичность игрока, правила, вложенный счёт и финальное состояние. Проверка не ограничивается совпадением хеша: сервер заново проигрывает ввод и сравнивает каждую контрольную точку. SQL сначала выбирает не более 20 лучших результатов, по одному на игрока; каждый выбранный журнал также проходит проверку.

Перед публикацией сервер дополнительно проверяет принадлежность proof именно этому испытанию, назначение `creator-proof` и победу. Регрессия с двумя настоящими выигранными proof и повреждённой связью подтверждает отказ `409`; испытание остаётся в состоянии `VALIDATED`.

Реальные обрывы ответа после SQLite commit выявили две ошибки восстановления клиента. Ответ `401` на повтор больше не стирает ключ незавершённой операции: повторный вход тем же пользователем возвращает исходные challenge/match с `replayed: true`. Ошибка `503` при чтении состояния больше не стирает сохранённый matchId после успешного чтения challenge. До полного восстановления новый заезд заблокирован; кнопка повторного чтения и reload возвращают прежний заезд. SQLite-проверки подтверждают отсутствие дубликатов. Успешные игровые ответы в этих сценариях не подменяются.

Первая общая raw-матрица дала 39 passed / 1 failed: в мобильном зачётном заезде перестало проходить касание. Отдельный воспроизводимый сценарий выявил соответствующую симптомам гонку: фоновый GET каждые 2,5 секунды временно отключал кнопки через общий `busy` между `touchstart` и `touchend`. Сервер не получал запрос хода, поэтому увеличение timeout не могло исправить этот дефект. Трасса событий первоначального общего прогона не сохранялась; его точное расписание касания и GET не восстанавливается задним числом. Фоновое чтение теперь выполняется отдельно от блокировки записей. Ответ применяется только к исходным match, actor и token; проверка sequence не позволяет старому снимку откатить уже подтверждённый ход. Записи сохраняют прежнюю сериализацию и ключи idempotency.

Сервис не включает платежи, внешнюю публикацию, рейтинговую экономику или proxy на production. В CLI Core он выключен по умолчанию. Файлы Unity остаются отдельным экспортом.

## Core: резервная копия и реальное восстановление

Общий модуль `server/core_backup.py` использует SQLite online backup и создаёт самостоятельный снимок. Простое копирование mainfile активной WAL-базы запрещено в offline-проверке. Проверяются целостность SQLite, внешние ключи, структура Core, размер и SHA-256, а затем формируется связанная пара файла базы и manifest.

Восстановление разрешено только в новый каталог вне известных production/public корней. Существующие файлы и симлинки не перезаписываются. Пользователь может дополнительно указать собственный защищённый корень. Manifest связывает имя снимка, размер, хеш и схему; независимо сохранённый SHA-256 принимается как дополнительное условие. В отчёте честно указано, что сама пара файлов не является криптографической подписью отправителя.

`scripts/core-recovery-drill.py` поднимает два отдельных штатных процесса Core на временных loopback-портах. Учётные записи, проект, участник, версии, задания, ассеты и запись затрат создаются через HTTP. Удержанный read transaction заставляет новые данные оставаться в WAL: в основном файле ещё нет проекта, но работающий API его уже видит. Online backup должен сохранить это состояние.

После снимка исходный проект изменяется ещё раз. Восстановленный сервер должен показать версию именно на момент резервирования. Проверяются вход и существующая хешированная сессия, права owner/viewer/outsider/anonymous, связи ассетов с версиями, результат задания, повтор ключа операции без дублирования затрат и новая запись через восстановленный API. После остановки процесса снова проверяются сохранность записи, SQLite integrity и FK.

Этот цикл использует новые локальные данные. Он не означает восстановления настоящей production-копии и не измеряет production RTO/RPO. В CI публикуется только обезличенный JSON-отчёт. Рабочий каталог с SQLite, хешами паролей и сессиями не включается в artifacts.

Подробные команды оператора приведены в `CORE-RECOVERY-DRILL.md`.

## Воспроизведение

Из корня репозитория, с Node 22 и Python 3.12:

```bash
npm ci
npm run build:games
npx playwright install chromium
npm run qa:godot-export
npm run qa:games-local
npm run qa:remix-server
npm run qa:remix-ui
```

`qa:games-local` создаёт собственный временный Core/REMIX сервер, использует настоящие Core-сессии и удаляет временную базу после завершения. Браузерные API-записи разрешены только на точный origin этого сервера. Внешние POST/PUT/DELETE блокируются до отправки и отражаются в отчёте.

Проверка того же сайта с Pages-доставкой:

```bash
node scripts/compress-pages-wasm.mjs dist
npm run qa:godot-export
npm run qa:cloudflare-pages
npm run qa:games-local -- --cloudflare-headers --out test-results/packaged-games
```

Полный Core drill, с новыми путями при каждом запуске:

```bash
python3 scripts/core-recovery-drill.py \
  --work-dir /tmp/osgard-core-recovery-review \
  --report /tmp/osgard-core-recovery-review.json
```

## CI и границы вывода

Frontend browser CI проверяет обычный Web export и реальные игровые API. Full Source Release Acceptance отдельно проверяет упакованные байты, затем формирует и проверяет ZIP/manifest и сохраняет точный кандидат. Cloudflare workflow сохраняет полный проверенный Pages-пакет. Core recovery workflow исполняет HTTP drill и сохраняет только безопасный отчёт.

Сохранение Pages-пакета включает `.vite/manifest.json`: для проверенного `dist` явно включены hidden files в upload-artifact. Декларативный archive checker проверяет HTML/CSS-зависимости; исполняемые Godot-зависимости дополнительно покрыты обязательным `qa:godot-export`, браузерным сценарием основного маршрута и общим per-file manifest.

Матрица проверяет заявленные действия каждого клиента. Например, INHERIT проходит размещение и сохранение локального следа; общий серверный мир в этой изолированной среде возвращает `401` и остаётся `unavailable` в JSON. Необязательные analytics POST на другой origin блокируются до отправки и остаются `not-tested`. Успех локального сценария не подменяет состояние этих интеграций.

Native smoke, браузерная приёмка, Web export и архивная проверка отвечают на разные вопросы. Их успешное завершение не заменяет опубликованный staging, реальные устройства Android/iOS, проверку рабочего внешнего сервиса или отдельное восстановление production-backup.
