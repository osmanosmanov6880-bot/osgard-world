# OSA CINEMA V64 — RELIABILITY & INTEGRITY CORE

**Дата подготовки:** 29 октября 2026. **Основа:** master после объединения PR #641, #652, #655, #658, #661, #665, #674. **Ветка V64:** feature/osa-cinema-v64-integrity-recovery-20261029.

V64 — это действительно реализованные серверные контроли, реальный операционный инструмент и пример конфигурации развёртывания, **не** заявка на состоявшийся глобальный хостинг и не подтверждение кино-релиза.

## Крупный блок A — общая файловая квота владельца

В V63 было 32 МиБ и 16 файлов на кинопространство, 8 МиБ на файл. V64 добавляет **64 МиБ на владельца** поверх всех его кинопространств, включая файлы, загруженные редакторами.

Проверка запускается внутри `BEGIN IMMEDIATE` перед записью BLOB в SQLite, чтобы одновременные загрузки в разные пространства не превышали общую квоту. Неавторизованные люди не получают статистику чужих файлов. `GET /api/core/cinema/storage/overview` возвращает только данные текущего аккаунта, а личный реестр Vault показывает владельцу общий баланс и оставшееся место.

Это осознанный лимит **self-hosted пилота**, а не архитектура CDN или неограниченное облачное хранилище.

## Крупный блок B — проверка целостности по запросу

Новый GET `/api/core/cinema/spaces/{spaceId}/vault/integrity` доступен только **владельцу пространства**. Сервер повторно хеширует настоящие байты всех файлов указанного пространства и сравнивает длину и SHA-256 с метаданными SQLite. При расхождении возвращается `FAIL` с точным счётчиком повреждённых записей, но без раскрытия файла. Скачивание повреждённого файла по-прежнему блокируется отдельной проверкой V63.

В интерфейсе File Vault: реальная кнопка «Проверить целостность / Check stored bytes», отчёт PASS/FAIL, дата и число проверенных файлов, предупреждение о том, чего проверка не подтверждает. Наблюдатель и редактор не получают доступ к этой операции.

**Граница доказательства:** проверяется совпадение текущих байтов в текущей SQLite с хешем, который хранится в *той же SQLite*. Администратор, подменивший одновременно байты и хеш, не обнаруживается таким отчётом. Это не криптографически независимая цепочка хранения, не AV-сканирование и не юридическая проверка прав.

## Крупный блок C — настоящий backup и restore drill

`scripts/osa-cinema-v64-recovery-drill.py` создаёт **согласованный online SQLite backup** через существующий `core_backup.backup` без остановки транзакционного источника, защищает готовый файл правами `0600`, проверяет SHA-256 всей резервной копии, затем открывает её как **отдельный read-only SQLite** и запускает:

- `PRAGMA integrity_check` и `PRAGMA foreign_key_check`;
- проверку длины и SHA-256 **каждого реального BLOB** в сохранённом архиве;
- строгий отказ при повреждении, существующей цели или попытке разместить исходную БД/резервную копию в каталоге `dist`.

Результат — машинный JSON без содержимого файлов: `status=PASS|FAIL`, хеш бэкапа, количество BLOB, нарушений и контроль готовности. **В живой production-файл восстановление не выполняется**: это проверяемая независимая копия, а не опасное автоматическое переключение сервиса. Должен существовать отдельный операторский регламент восстановления с проверкой идентичности владельца и времени простоя.

## Крупный блок D — операционные шаблоны

`deploy/osa-cinema-v64/` содержит:

- пример `Caddyfile` с HTTPS, HSTS и no-store для API;
- системный сервис Linux с непривилегированным пользователем, localhost-only Python, приватным `StateDirectory`, `UMask=0077` и ограничениями systemd;
- **неактивированный** timer и скрипт одноразового локального бэкапа;
- эксплуатационный README с последовательностью введения в работу.

Эти файлы **не означают**, что кто-то реально создал DNS, сервер, TLS-сертификаты или включил бэкапы. Они подготавливают технически конкретный deployment-путь.

## Чего всё ещё нет для мира

Настоящей облачной инфраструктуры, региональной отказоустойчивости, защищённого объектного хранилища, **шифрования BLOB на уровне приложения и бэкапов**, KMS, антивируса, безопасного transcoding, CDN, DRM, организованного response-to-incidents, юридического документооборота, независимой проверки авторских прав, доказанной ёмкости, мониторинга SLA и реальной публичной премьеры.

Существующие PDF/MP4 в Vault являются **приватными рабочими файлами**, не коммерчески выпущенными фильмами. ZERO WINDOW остаётся 0/13 независимо подтверждённых отснятых сцен. Производственный релиз публичного кино — **NO-GO**.

**Следующий ключевой шаг после V64:** внедрение шифрования с безопасной миграцией старых BLOB, KMS, ограниченной загрузки по отдельным очередям и настоящего развёртывания с HTTPS + независимым end-to-end тестом. Нельзя объявлять это уже сделанным.
