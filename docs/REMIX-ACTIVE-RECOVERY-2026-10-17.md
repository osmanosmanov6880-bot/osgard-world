# Core REMIX arena: активный заезд, восстановление и история

Дата: 2026-10-17. Статус: локальные проверки пройдены; этот отчёт не является
подтверждением production-развёртывания или удалённого CI для нового commit.

В кандидате PR128 закрыт воспроизведённый дефект: активный заезд мог продолжаться
из повреждённого сохранённого состояния, не соответствующего журналу ходов.
Теперь чтение состояния, новый ход и повтор подтверждённого хода проверяют весь
префикс журнала. Отдельный запуск реального Core по HTTP подтвердил восстановление
активного заезда из online SQLite backup, сохранение владельца и сессий,
идемпотентность повтора и точное совпадение продолжения, результата и replay.
История собственных заездов позволяет найти заезд после потери браузерной ссылки.

## Прежний дефект и исправление

Исходник до исправления получен из PR128:

```sh
git show 02a08becdb6047bf8363f4e9408ef9dbd209ae75:server/remix_service.py
```

Его SHA-256:
`1cbd2cce92c7ca96ae00e0de873e77ca511d9a2927fad74a6e0a930bd8f9665f`.

В одноразовой локальной базе первый подтверждённый ход приводил в `[1, 3]`.
После замены только сохранённой позиции на `[7, 3]` старый `GET state` возвращал
200 с этой позицией. Следующий ход `sequence: 2` также возвращал 200, сохранял
позицию `[8, 3]` и вторую строку журнала. Воспроизведение исходных ходов должно
было дать `[2, 3]`. Прежняя проверка завершённого replay не защищала этот активный
переход. Воспроизведение выполнялось только с временными данными.

Новый `verified_prefix` в
[server/remix_service.py](../server/remix_service.py) начинает с начального
состояния и проверяет арену, непрерывную последовательность, нормализованный
intent, каждый checkpoint и его хеш, каждое сохранённое подтверждение, полное
состояние и фазу. У активного заезда должны отсутствовать результат и replay hash.
Для завершённого заезда также проверяются производный результат и полный replay.

Проверка выполняется перед `GET matches/:id/state`, новым input и возвратом
сохранённого input-ответа по `Idempotency-Key`. Повтор того же sequence с новым
ключом тоже проходит проверку. Повреждение возвращает `503 replay_integrity`;
match/input/operation rows остаются неизменными. Корректный повтор возвращает
исходное подтверждение, без дополнительного хода. Его исторический sequence
не должен откатывать уже более новое подтверждённое состояние клиента.

Префикс читается из одного snapshot соединения. Пишущая транзакция удерживает
`BEGIN IMMEDIATE` на время проверки и продолжения; проверенный префикс не
кешируется между соединениями.

## История заездов и возвращение из браузера

`GET /api/core/remix/v1/matches` требует Core bearer и возвращает только заезды
текущего аккаунта. `status=active` выбирает `PLAYING`, `status=complete` — `RESULTS`.
По умолчанию выдаются 20 активных заездов; `limit` разрешён от 1 до 50. Сортировка
идёт по `createdAt` и ID по убыванию, SQL читает не более `limit + 1` строк.
`nextCursor` содержит последний выданный ID при наличии продолжения либо `null`.
Курсор принадлежит тому же аккаунту; завершение заезда между страницами не делает
его недействительным. Отдельные страницы не обещают общий неизменный snapshot.

Summary содержит только `id`, `challengeId`, `title`, `phase`, `purpose`,
`createdAt`, `stateVerified: false`. Это ссылка для последующего проверяемого
открытия; результат, позиция и журнал в список не включены. Повреждённый заезд
может присутствовать в истории, но его `GET state` завершится 503. Чтение истории
не создаёт заезд и не меняет Core или arena rows.

Query ограничен 256 символами и тремя известными полями, каждое не более одного
раза. Неизвестные, дублированные, пустые или синтаксически неверные поля, `limit=0`,
`51`, `NaN` и некорректный cursor отвергаются с 400. Чужой и отсутствующий cursor
получают одинаковый `invalid_cursor`. Анонимный запрос получает 401. Неверные
версии/пути и legacy namespace не попадают в обработчик истории Core arena.
HTTP dispatch находится в [server/core_server.py](../server/core_server.py).

В интерфейсе реализован список активных и завершённых заездов с проверяемым
открытием. Четыре новых сценария в
[scripts/remix-ui-regressions.mjs](../scripts/remix-ui-regressions.mjs)
прошли в составе полного `npm run qa:remix-ui`:

1. Удаление браузерного сохранённого состояния, повторный вход и восстановление
   того же заезда через историю; другой аккаунт не видит его в своём списке.
2. 21 заезд на двух страницах без дублей, включая допустимое сервером название
   из 100 Unicode code points вне BMP; ограниченная высота списка и отсутствие
   горизонтального переполнения на мобильном viewport.
3. Открытие завершённого результата и replay без создания нового заезда.
4. Ошибка 401 фонового запроса истории одновременно с реальным input, уже
   записанным сервером: подтверждение 200 сохраняется и не возникает второго хода.

Полный набор завершился **14/14 PASS**, `npm run build` также прошёл. Мобильный
скриншот восстановленного заезда при ширине 390 px просмотрен: пересечений и
обрезки элементов не обнаружено. Эти результаты отдельны от HTTP recovery drill.

## Активный recovery drill: snapshot и граница подтверждения

Исполняемый сценарий:
[scripts/remix-recovery-drill.py](../scripts/remix-recovery-drill.py).
Он использует существующие guarded backup/restore helpers и `LocalCore` из
[scripts/core-recovery-drill.py](../scripts/core-recovery-drill.py), добавляя
явное `enable_remix=True`. Значение по умолчанию у helper остаётся `False`.

Опубликован точный очищенный JSON отдельного запуска:
[remix-active-recovery-local-2026-10-17.json](evidence/remix-active-recovery-local-2026-10-17.json).
SHA-256 файла:
`c89a1c36b5fdd83a645d2f408ea8b0d53f317aa6d75299fc85e224e053d92f5b`.
Запуск: **2026-10-17 18:28:26.136980–18:28:27.652620 UTC**. Общее локальное время —
1515.66 ms; это длительность синтетического упражнения, а не production RTO.

| Этап | Наблюдение и критерий |
| --- | --- |
| Первый Core | Созданы три аккаунта: creator, challenger, outsider. Creator завершил proof из 13 ходов, валидировал и опубликовал challenge. Challenger подтвердил четыре хода и остался `PLAYING`. |
| Online backup | Удерживаемый WAL reader делает основной файл SQLite устаревшим: в нём ещё нет матчей, тогда как данные есть в WAL. Небезопасный offline copy отвергнут; SQLite online backup содержит точный активный префикс 4. |
| После snapshot | Исходный Core принимает и подтверждает ход 5, затем получает настоящий SIGKILL. |
| Второй Core, та же исходная база | Восстановлен подтверждённый sequence 5. Повтор с исходным ключом возвращает тот же ACK. Исходный заезд завершается до sequence 13 и становится эталоном продолжения. |
| Третий Core, отдельное восстановление backup | Проверены парольный вход, все три сохранённые сессии и ownership. Восстановлен ровно sequence 4; более поздний исходный ход 5 в backup отсутствует. |
| Повтор и продолжение | Последний ход snapshot повторён с исходным ключом и с новым ключом/тем же sequence без дополнительного input. Изменённый payload с прежним ключом получает 409. Все девять последующих подтверждений совпадают с эталонным продолжением. |
| Завершение | Итоговый sequence 13, результат и полный replay совпадают с исходным заездом; replay повторно воспроизводится. Проверены leaderboard, исключение creator proof из рейтинга, закрытый доступ outsider и отказ нового хода после завершения. |
| Четвёртый Core, повреждённая независимая копия | Только в этой копии подменена активная позиция. `GET state`, свежий input и cached retry получают `503 replay_integrity`; все строки четырёх arena-таблиц остаются неизменными. |
| Финальные проверки | SQLite `integrity_check` и `foreign_key_check` пройдены. Восстановление и повреждённая ветка не изменили исходную базу, backup или manifest. |

**Две границы проверены раздельно.** Crash/restart исходной базы сохраняет уже
подтверждённый ход 5. Восстановление более раннего backup возвращает ход 4, поэтому
исключение хода 5 в этой ветке — ожидаемая точка восстановления. Запуск не обещает
нулевую потерю данных после произвольного старого backup.

В snapshot: три пользователя, один challenge, два заезда и 17 input rows
(13 creator proof + 4 challenger). Backup — 593920 bytes; restored SQLite сохраняет
`user_version: 1`, 48 таблиц и тот же schema hash после продолжения.

## Пределы и совместимость существующих данных

Игровые правила остаются `remix-arena-v1`: поле 12 × 7, шаг 100 ms, до 40 объектов
и максимум 256 inputs. Префикс проверяется одним проходом; SQL `LIMIT 257`
обнаруживает переполнение, не загружая неограниченный журнал. Каждый хранимый JSON,
который разбирает проверка префикса или cached input-ответа, ограничен 16 KiB в
UTF-8. Дублированные ключи, non-finite числа и несоответствие
канонических типов отвергаются. Проверки покрывают пустой активный префикс,
рестарт, граничные 256 ходов и выход за лимит.

Отдельная одноразовая проверка совместимости создала старым сервисом из `02a08bec`
заезд с 40 объектами, предельной длиной object IDs и 100-символьным Unicode title.
Из одной базы созданы две SQLite backup-копии; старый и новый сервис продолжены
одинаковыми запросами. **15 сериализованных response bodies совпали побайтово**,
включая state, retries, новые input, result и replay. Совпали все строки четырёх
таблиц: `remix_challenges`, `remix_matches`, `remix_inputs`, `remix_operations`.
Миграция схемы для этого изменения не потребовалась.

Эта проверка сохранена как результат локального выполнения, без отдельного
standalone-скрипта или JSON-артефакта. Она подтверждает проверенный старый формат и
граничные размеры; не является аудитом всех ранее существовавших баз. Постоянные
регрессии находятся в service suite. SHA-256 обнаруживает несоответствие данных,
но не является секретной подписью или защитой от администратора, который может
согласованно переписать всю базу.

## Воспроизведение и границы отчёта

```sh
python3 -m unittest discover -s tests -p test_remix_service.py -v
python3 -m unittest discover -s tests -p test_remix_history_http.py -v
python3 -m unittest discover -s tests -p test_remix_recovery_http.py -v

# Требуются новые, ещё не существующие пути.
python3 scripts/remix-recovery-drill.py \
  --work-dir /tmp/osgard-remix-active-recovery-example \
  --report /tmp/osgard-remix-active-recovery-example-report.json

npm run build
npm run qa:remix-ui
```

Drill сам запускает Core с `--remix` на loopback и создаёт новые синтетические
данные. Путь к готовой рабочей базе или внешний URL он не принимает. В publishable
report присутствуют только безопасные агрегаты, проверки, длительности и хеши.
Рабочий каталог с тестовой базой, аккаунтами и сессиями не публикуется. При ошибке
в отчёт попадают фиксированная стадия и тип исключения, без сырого сообщения.

`production_backup_used`, `production_modified`, `production_restore_tested`,
`production_rto_rpo_measured`, `external_requests_performed` и
`legacy_active_match_recovery_tested` в приложенном JSON равны `false`.
Реальный production backup, восстановление legacy engine, синхронный multiplayer
и новая production-доступность этим свидетельством не подтверждаются.
