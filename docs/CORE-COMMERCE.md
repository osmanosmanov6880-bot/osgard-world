# OSGARD Core Commerce — подготовленный цикл разовой покупки

## Статус поставки

Подготовлен серверный модуль, интерфейс оператора в `/workspace` → Business и страница покупателя `/purchases`. **По умолчанию Commerce выключен.** Этот релиз не выбирает подключённый Stripe-аккаунт, не записывает платёжные секреты, не принимает реальную оплату и не выполняет реальный возврат.

Область первой реализации: один настроенный торговый аккаунт, один локальный пользователь-оператор, существующий локальный аккаунт покупателя, разовая покупка одного сохранённого HTML. Поддерживаются USD и EUR, сумма хранится целым числом центов. RUB явно отклоняется. Это не подписка на обучение, не маркетплейс, не хостинг и не подключение произвольных продавцов.

Проверены локальный HTTP/SQLite-цикл с FakeProvider и настоящий SDK Stripe 15.6.0 с перехваченным транспортом без сети. Эти проверки **не являются реальным sandbox-платежом Stripe или подтверждением готовности live-аккаунта**.

## Что получает пользователь

1. Оператор сохраняет предложение и создаёт обычный черновик заказа.
2. HTML собирается по текущему контракту и фиксируется как внутренний выпуск. Другой участник принимает именно этот выпуск.
3. Оператор выбирает черновик, принятый выпуск и логин покупателя. Отдельно подтверждает точную сумму, валюту и состав передаваемого HTML.
4. Сервер копирует название, состав предложения, исходную версию, HTML и его SHA-256 в неизменяемый конверт заказа.
5. Заказ появляется только у выбранного покупателя. Кнопка оплаты открывает размещённую у Stripe страницу Checkout.
6. Возврат браузера на `/purchases` лишь показывает состояние. Доступ выдаёт сервер после подходящего подписанного события и сверки текущих объектов Stripe.
7. Скачивание снова проверяет аккаунт, право доступа и целостность конверта. Покупатель получает только HTML своего заказа, а не проект, источники, внутренние заметки или чужие заказы.
8. Оператор может запросить частичный либо полный возврат. Сумма возврата и доступ изменяются после серверного подтверждения. Полный возврат отзывает новое скачивание; уже скачанную копию удалённо отозвать невозможно.

Последующее изменение проекта, сборка нового HTML или восстановление версии не подменяют оплаченный файл. Обычная отмена черновика, уже связанного с Commerce, блокируется: она не может изображать отмену существующего Checkout.

## API

Все пути ниже имеют префикс `/api/core/`. Кроме подписанного webhook, нужен действующий Bearer-токен Core. Изменения требуют `Idempotency-Key` длиной 16–100 символов из `[A-Za-z0-9_-]`.

| Метод и путь | Доступ | Результат |
| --- | --- | --- |
| `GET commerce/config` | Любой вошедший пользователь | Включение, режим, USD/EUR, возможность управления; без ключей и ID аккаунта Stripe |
| `GET projects/{projectId}/commerce` | Настроенный оператор и владелец проекта | Коммерческие заказы данного проекта, подтверждённые оплаты, возвраты и доступ |
| `POST projects/{projectId}/commerce` | Настроенный оператор и владелец проекта | Подготовка конверта: `expectedVersion`, `draftOrderId`, `releaseId`, `buyerUsername`, `confirmedAmountMinor`, `confirmedCurrency`, `sharingAcknowledged:true` |
| `GET commerce/purchases` | Покупатель | Только его заказы в текущем аккаунте Stripe и режиме |
| `POST commerce/orders/{orderId}/checkout` | Покупатель этого заказа | Создание/повтор той же Checkout-операции; `{url}` либо явное `pending`/`closed` состояние |
| `POST commerce/orders/{orderId}/refund` | Настроенный оператор и владелец проекта | `targetRefundMinor`: желаемый **общий** подтверждённый возврат с учётом предыдущих |
| `GET commerce/purchases/{orderId}/file` | Покупатель с действующим оплаченным доступом | `orderId`, `title`, `html`, `sha256`; никаких внутренних материалов проекта |
| `POST commerce/webhook` | Подпись Stripe, без Core-сессии | Атомарное применение подтверждённого события |

Пример возврата: цена 1 000 центов, уже подтверждено 300 центов возврата. Запрос `targetRefundMinor:1000` создаёт возврат оставшихся 700 центов. Повтор с той же целью не возвращает ещё 700.

Публичный `/health` сообщает `payments` как состояние включения конфигурации, `paymentMode` и `livePaymentTested:false`. Он не выполняет сетевую проверку аккаунта и не удостоверяет готовность Stripe.

## Достоверное состояние и восстановление

Состояние хранится в той же серверной SQLite, а не в браузере. Миграция добавляет таблицы, сохраняя существующий Core API и данные версии 1.

| Таблица | Назначение |
| --- | --- |
| `commerce_orders` | Цена, валюта, оператор, покупатель, аккаунт/режим, принятый выпуск, неизменяемый конверт и накопленные суммы |
| `commerce_checkout_ops` | Одна Checkout-операция на заказ, неизменяемые параметры, постоянный ключ Stripe, lease, известный session ID и URL |
| `commerce_refund_ops` | Постоянный ключ возврата на суммарную цель, параметры, статус и refund ID |
| `commerce_webhook_events` | Уникальный event ID и SHA-256 исходного тела события |
| `commerce_entitlements` | Право конкретного покупателя скачать конкретный конверт |
| `commerce_requests` | Привязка клиентского ключа к точному запросу и сохранённому ответу |

Ключ внешней операции и её параметры записываются **до** вызова Stripe. Запрос выполняется вне SQLite-транзакции; lease ограничивает параллельный запуск. При потере ответа сервер повторяет те же параметры с прежним ключом. Перезапуск сервера или новая вкладка не создаёт новую платёжную операцию.

Неизвестную операцию можно повторить в течение 20 часов от первого запроса. Затем нужна ручная сверка; новый ключ автоматически не выдаётся. Это оставляет запас до минимального 24-часового хранения ключей идемпотентности Stripe. Удалять строки, менять ключи или сбрасывать неизвестное состояние ради повторного запроса нельзя.

Поздний ответ создания Checkout не меняет `expired`, `failed`, `payment_processing`, `paid` или `refunded` обратно на открытый заказ. Если webhook пришёл раньше HTTP-ответа, известный session ID без URL даёт явное состояние ожидания. Позднее неподтверждённое событие не открывает закрытый заказ.

Возврат, пришедший раньше ответа `refunds.create`, связывается с заранее сохранённой операцией по метаданным из актуального объекта Stripe. Сопоставляются заказ, операция, PaymentIntent и точная сумма. Состояния `failed` и `confirmed` защищены от поздних ответов и более старых результатов сверки. Неуспешный возврат требует ручной сверки перед новой операцией.

## Подтверждение платежей и возвратов

Webhook проверяется по точным полученным байтам: HMAC SHA-256, подпись `v1`, timestamp с окном ±300 секунд, затем JSON. Подписанная строка не собирается заново из разобранного JSON. Предельное тело — 256 КиБ.

Проверяются API-версия, `livemode`, привязка аккаунта и неизменяемые метаданные заказа. У direct-account события поле `event.account` может отсутствовать. Для этой схемы аккаунт дополнительно подтверждает реальный adapter через `client.v1.accounts.retrieve_current()` (`/v1/account`), сопоставляя его с настройкой. Это проверка без предположения о Connect.

Право доступа выдаётся только для `checkout.session.completed` или `checkout.session.async_payment_succeeded`, когда актуальная полученная Checkout Session имеет `payment_status=paid` и `status=complete`. Сверяются сумма/валюта, client reference, режим, метаданные, текущий успешный PaymentIntent, полная `amount_received`, оплаченный и захваченный Charge. GET success page и один лишь факт наличия session ID доступа не дают.

Обработчик получает текущие Session/PaymentIntent/Charge и список возвратов через подготовленный provider. Для денег учитываются только возвраты со статусом `succeeded`; `pending`, `failed` и `canceled` не засчитываются. Сумма подтверждённых возвратов монотонна, не превышает цену заказа и не уменьшается при доставке старого события. Полный возврат не оживает после позднего события об оплате.

Event ID уникален. Точное повторение возвращает сохранённый результат, повтор ID с другим телом отклоняется. Запись события и обновление денег/прав выполняются в одной транзакции. Временная недоступность Stripe возвращает ошибку, чтобы событие могло быть повторено; успех до завершения сверки не отправляется.

События, которые нужно подключить в snapshot webhook версии **2026-08-26.dahlia**:

- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`
- `checkout.session.async_payment_failed`
- `checkout.session.expired`
- `charge.refunded`
- `refund.created`
- `refund.updated`
- `refund.failed`
- `charge.refund.updated` — если используется этим webhook endpoint

## Конфигурация оператора

Зависимость сервера: `stripe==15.6.0`. Используется `StripeClient`, публичный `RequestsClient` с timeout 20 секунд и сетевыми повторами SDK, выключенными в пользу постоянных ключей приложения. Преобразование объектов SDK выполняется через `.to_dict()`. `payment_method_types` не задаётся: способы оплаты определяет настроенный аккаунт Stripe.

| Переменная | Значение / смысл |
| --- | --- |
| `OSGARD_COMMERCE_ENABLED` | `0` по умолчанию; только `1` включает новые внешние запросы |
| `OSGARD_COMMERCE_MERCHANT_USER_ID` | ID существующего локального пользователя-оператора |
| `OSGARD_STRIPE_ACCOUNT_ID` | Подтверждённый аккаунт `acct_…` |
| `OSGARD_STRIPE_LIVEMODE` | `0` по умолчанию; `1` только после отдельного решения о реальных платежах |
| `OSGARD_COMMERCE_PUBLIC_ORIGIN` | HTTPS origin опубликованного Core без пути, query или fragment |
| `OSGARD_STRIPE_API_KEY` / `OSGARD_STRIPE_API_KEY_FILE` | Секретный или ограниченный ключ выбранного аккаунта и режима; файл имеет приоритет |
| `OSGARD_STRIPE_WEBHOOK_SECRET` / `OSGARD_STRIPE_WEBHOOK_SECRET_FILE` | Секрет подписи именно настроенного endpoint; файл имеет приоритет |

Ключ с префиксом `test` нельзя использовать при `LIVEMODE=1`, и наоборот. Секреты не возвращаются клиенту, не включаются в журнал или репозиторий. Подключение через `/etc/osgard/core-commerce.env` готовит окружение развёртывания; файл создаёт оператор с закрытыми правами после выбора аккаунта и условий.

При временном отключении Commerce сохраняйте merchant ID, account ID и режим: это позволяет читать историю и проверять ранее выданный доступ. **Отключение модуля не отменяет уже созданные Checkout URL у Stripe.** Webhook во время отключения также возвращает ошибку; незавершённые события требуют доставки после восстановления конфигурации. Остановка новых запросов приложения не заменяет сверку уже начатых платежей.

## Экономика и границы запуска

Обычные `data.orders` остаются редактируемыми черновиками; они не превращаются в оплаченные заказы и не служат источником выручки. Commerce показывает подтверждённые суммы из своей таблицы отдельно по валютам, вычитает подтверждённые возвраты и затем введённые расходы проекта в той же валюте. В тестовом режиме числа явно помечены как тестовые.

Комиссии Stripe автоматически не загружаются. Расходы вычислений, платёжной инфраструктуры, наставников и поддержки нужно внести в существующий журнал, прежде чем оценивать вклад формата. Старые агрегаты `CoreProject.economics` и overview сохраняются для совместимости как расчёт черновиков/ручных расходов; интерфейс больше не выдаёт их нулевую выручку за сводку Commerce.

В этой версии не реализованы подписки, Connect/маркетплейс, выдача доступа ко всему курсу, налоговая автоматизация, письма, автоматическая отмена Checkout, самостоятельное восстановление старых неизвестных операций, обработка chargeback/dispute и спорных платежей. Интерфейс не обещает эти функции. Изменения платежей из Dashboard требуют доставки и сверки webhook; перед новым возвратом сверяется текущая сумма и отсутствие незавершённых возвратов.

Для включения реальных платежей остаются внешние условия: выбор и проверка торгового аккаунта, подтверждение цен и условий предложения, настройка endpoint/секретов и реальное sandbox-испытание полного цикла с журналом доказательств. Учебный платный пилот, интервью, результаты учеников, возвраты клиентов, маржинальность и цели 3×/85% этим кодом не достигнуты.

## Проверки и источники

`python3 scripts/core-commerce-smoke.py` — 25 локальных HTTP/SQLite тестов с FakeProvider: авторизация, неизменяемый оплаченный файл, отсутствие доступа по return URL, подпись и режим/аккаунт, сумма/валюта/метаданные, повтор события, потеря ответа и перезапуск, один Checkout при конкуренции, частичный/полный возврат, возврат раньше оплаты, pending/failed, сверка внешнего возврата, четыре вида гонок с поздними ответами, отключение при сохранении оплаченного доступа.

`python3 scripts/core-stripe-sdk-smoke.py` — реальная поверхность SDK 15.6.0, 7 перехваченных transport requests без сети: import/конструктор, собственный аккаунт, Checkout, PaymentIntent, Charge, refunds, версия API и idempotency headers.

Машиночитаемый результат: `CORE-COMMERCE-TESTS.json`. SDK-проверка печатает итог PASS и число перехваченных запросов в журнал запуска.
