# INHERIT: аккаунт, поколения и передача мира

## Состояние этого изменения

Этот документ описывает новый серверный контракт и его проверку в исходниках.
Публикация и проверка живой версии фиксируются отдельно в журнале выпуска;
наличие этого файла само по себе не доказывает deployment.

Реализуемый сценарий: открыть мир → найти следы → изменить → сохранить поколение
→ передать следующему хранителю → получить уведомление об изменении → вернуться
и увидеть новое поколение. Одновременно мир изменяет один хранитель. Это
последовательное наследование; совместного редактирования одного поколения нет.

## Модель данных и прав

`server/core_inherit.py` подключён к существующему Core API и его SQLite.
Проверенная Core-сессия определяет автора. Свободное локальное имя, номер
поколения из архива, world ID или ссылка не предоставляют прав.

Новый мир получает собственный ID, ревизию 1 и текущее поколение 1. Создатель
становится первым хранителем. Локальная копия может дать только исходные объекты
с происхождением `local-copy`; локальные и художественные записи истории не
превращаются в подтверждённые поколения. Шаблон `quiet-reach-v1` начинает без
пользовательских следов. Фиксированный декор острова остаётся частью шаблона.

Клиент отделяет базовые объекты от незавершённого delta. Копирование текущего
локального мира не должно одновременно включать pending-объекты в базу и затем
повторно добавлять их при завершении поколения.

Сохранение атомарно дописывает запись поколения, полный снимок объектов,
delta, автора, сообщение, время, parent hash и snapshot hash. Оно увеличивает
ревизию и номер текущего поколения. В той же транзакции создаются уведомления
предыдущим хранителям и запись результата операции. `BEGIN IMMEDIATE` и
проверки `expectedRevision`/`expectedGeneration` допускают ровно один результат
для двух одновременных запросов с одной исходной ревизией.

SQL-триггеры запрещают UPDATE/DELETE записей поколений. Хэши связывают снимки
в линейную цепочку и позволяют сверять сохранённые данные. Они не являются
подписью независимого наблюдателя, проверкой игрового replay или доказательством
происхождения импортированных объектов.

### Передача

Текущий хранитель указывает Core account ID получателя и явно подтверждает
передачу и сохранение доступа прежних хранителей к истории. Передачу можно
предложить после сохранения хотя бы одного своего поколения за текущий период
владения. До принятия или отмены редактирование приостановлено.

Получатель видит адресованное ему приглашение с названием мира и отправителем;
объекты приватного мира становятся доступны после явного принятия. Принятие
атомарно добавляет участника истории и назначает его единственным текущим
хранителем. Отправитель может отменить ожидающее приглашение, получатель —
отклонить. Приглашение истекает через семь дней. Ссылка сама по себе не даёт
доступа. При отказе получатель не получает снимок мира.

Все прошлые хранители сохраняют право чтения истории этого мира. После нового
поколения они получают уведомления внутри INHERIT. Эти действия не отправляют
почту, сообщения в мессенджерах или push-уведомления. Выход из Core немедленно
закрывает доступ для новых запросов с завершённой сессией, включая GET результата
ранее выполненной операции.

## API

Префикс: `/api/core/inherit/v1/`. Все маршруты требуют Core bearer; токен
передаётся только в Authorization на этом же origin. Каждый POST, кроме
отдельных стандартных auth-операций Core, требует `Idempotency-Key` из 16–100
латинских букв, цифр, `_` и `-`. Успешные POST возвращают HTTP 200.

| Метод и маршрут | Данные / результат |
|---|---|
| GET `capabilities` | Версия схемы, шаблон, модель прав и лимиты |
| GET `worlds` | Краткие сведения обо всех доступных мирах, до 256 |
| POST `worlds` | `{title, template, source, objects}` → `{world, operation}` |
| GET `worlds/{id}` | `{world}` со снимком, историей и правами текущего пользователя |
| POST `worlds/{id}/generations` | `{expectedRevision, expectedGeneration, message, delta}` → `{world, generation, operation}` |
| GET `worlds/{id}/generations/{number}` | Подтверждённое поколение и его полный снимок объектов |
| POST `worlds/{id}/handoffs` | `{expectedRevision, targetUserId, sharingAcknowledged:true}` → `{world, invitation, operation}` |
| GET `handoffs/{id}` | Приглашение только для отправителя или получателя |
| POST `handoffs/{id}/accept` | `{expectedRevision}` → новая роль хранителя, мир и приглашение |
| POST `handoffs/{id}/cancel` | `{expectedRevision}` → отмена отправителем |
| POST `handoffs/{id}/decline` | `{expectedRevision}` → отказ получателя; приватные объекты не выдаются |
| GET `notifications` | Уведомления пользователя и число непрочитанных |
| POST `notifications/{id}/read` | `{}` → отметка прочтения |
| GET `operations/{key}` | `{status:'committed', operation, result}` с результатом исходного POST |

Объект следа: `{type, x, y}`. Разрешены десять существующих инструментов игры;
координаты — конечные числа от 0 до 100, boolean не принимается как число.
Клиентский `author` и неизвестные поля не принимаются.

`world` включает `id`, `title`, `template`, `source`, `creator`, `custodian`,
`role`, `canEdit`, `canOfferHandoff`, `revision`, `currentGeneration`, `objects`,
`generations`, `pendingHandoff`, `baselineHash`, `snapshotHash`, `createdAt`,
`updatedAt`. Автор поколения — объект `{id, username}` из Core.

## Восстановление и локальная работа

Клиент сохраняет отдельное неизменяемое намерение до каждого POST. Неопределённый
ответ восстанавливается GET того же operation key; автоматического повторения
POST нет. HTTP 404 на GET операции означает отсутствие подтверждения, а не
доказательство, что исходный запрос не мог завершиться позднее. При 409 черновик
сохраняется; автоматического слияния с другим поколением нет.

Core хранит успешный ответ и проверяет повторное использование ключа с другим
телом. Запись INHERIT и общий журнал Core фиксируются одной транзакцией.
GET восстановления принадлежит аккаунту-инициатору и повторно проверяет доступ.
Если операция содержит приглашение и полный мир, обе проверки выполняются
независимо: адресованное приглашение не заменяет сохранённое членство в мире.
После подтверждения клиент запрашивает свежий мир: сохранённый ответ операции
может описывать прежнюю ревизию и прежнюю роль, если мир уже передан дальше.

Обычный локальный режим и его архив остаются отдельной веткой. Вход не публикует
локальный мир автоматически. Импорт не принимает чужой world ID как право
продолжить серверную историю. Возврат к исходному локальному миру и экспорт
копии сохраняют неизвестную серверную операцию исходного аккаунта. Экспорт
не даёт права продолжать ту же серверную историю без действующей сессии хранителя.

## Лимиты пилота и восстановление сервера

Лимиты: 32 созданных мира на аккаунт, 256 доступных миров, 1 024 пользовательских
объекта в мире, 100 новых следов за поколение, 128 сохранённых поколений,
64 хранителя в истории, 256 предложений передачи на мир. Входящие уведомления
хранят последние 200 записей; удаление старого уведомления не удаляет поколение.
Сохраняется общий предел Core: 10 000 успешных операций на аккаунт.

Добавлены собственные таблицы INHERIT без изменения Core `user_version=1`.
Предыдущая версия Core не обслуживает новые маршруты, но не переписывает эти
таблицы. Новый сервер отказывается запускаться, если частично утрачен набор
таблиц, обязательные столбцы, запись версии схемы или триггеры истории; он не
создаёт пустую таблицу прав поверх существующего мира. При отсутствии строки
членства чтение самого мира и восстановление содержащей его операции закрыты.
Проверка резервной копии допускает старые архивы
без INHERIT, но требует весь набор таблиц и триггеров, если обнаружена любая
из новых таблиц.

**Обновление от 18 октября 2026 года.** Проверка резервной копии теперь
сверяет не только таблицы SQLite и триггеры, но и все сохранённые цепочки
INHERIT: базовый снимок, delta, последовательность, parent/snapshot hashes и
текущее состояние каждого мира. Неправильный снимок отклоняется *до*
восстановления. Подробный порядок, аттестация счётчиков и границы проверки —
[INHERIT-BACKUP-SEMANTIC-VERIFICATION-2026-10-18.md](INHERIT-BACKUP-SEMANTIC-VERIFICATION-2026-10-18.md).


## Проверка

- `tests/test_core_inherit.py`: действительная SQLite, конкурентные сохранения,
  принятие/отмена передачи, ACL, недоступные чужие операции, immutable snapshots,
  откат при ошибке журнала/уведомления, восстановление резервной копии и реальный
  изолированный Core HTTP-обработчик.
- `tests/test_core_inherit_live_probe.py`: запрет повторов и передачи токена на
  другой маршрут, ограничения времени/размера, неопределённые auth/logout,
  совпадение новой зарегистрированной личности с `/auth/me`, подтверждение
  logout, режим только чтения и весь зонд на настоящем временном Core API.
- `scripts/core-inherit-gateway-smoke.py`: тот же цикл через кандидата Nginx
  и Core в disposable CI-контейнерах; реальные аккаунты только временного Core.
- `scripts/core-inherit-live-smoke.py`: по умолчанию GET-проверки. Выполнение
  операций требует `--exercise-inherit --expected-release <12 hex>`; создаёт
  два явно обозначенных QA-аккаунта и один личный мир, проверяет две генерации,
  уведомление, доступ и logout. Сохраняет только отчёт без учётных данных.

Браузерные fixtures проверяют поведение интерфейса, а отдельные API-проверки —
реальное серверное сохранение. Эти два вида доказательств не подменяют друг друга.
