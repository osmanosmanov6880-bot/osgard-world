# REMIX: контракт legacy-сервиса и новая защита публичного API

Дата проверки: **17 октября 2026 года**, 09:51:47–09:52:42 UTC. Адрес:
`https://osgard.world/api/remix`. Проверялась существующая матч-консоль,
подключённая через Nginx к `remix-api:8080`.

**Историческая проверка legacy-сервиса подтвердила изменение результата после
`RESULTS`. Для публичной границы API разработан отдельный исходный Python guard:
он проверяет фазу до ввода и сохраняет неизменяемый снимок завершённого матча в
SQLite.** Исходный Go-сервис не изменён. Разделы 1–6 фиксируют фактическое старое
поведение; разделы 8–9 описывают новую реализацию и её изолированные проверки.
Успешные локальные тесты сами по себе не означают, что guard уже включён на
`osgard.world`: свидетельства публикации и нового публичного прогона добавляются
отдельно после выполнения этих действий.

Unity-плеер `/games/remix/player/index.html` запускается отдельно. Ни этот
протокол, ни описанная HTTP-проверка не доказывают игровой процесс внутри Unity,
совместимость его физики с консолью или сетевой матч двух Unity-клиентов.

## 1. Что действительно проверено

Проверка создала приватное испытание с названием `OSGARD QA 2026-10-17` и один
матч с `maxPlayers: 2`. Все команды и запросы результатов относились только к
этому матчу и синтетическому игроку. В чужие матчи запросы не отправлялись;
рассылки, публикации приглашений и аналитические события не выполнялись.

Записанный прогон содержит **19 HTTP-запросов за 55,37 секунды**: 13 ответов
`200`, два `201` и четыре `409`. SHA-256 полного JSON-журнала наблюдений:

```text
a272459a3eaa2357b22ecc24d69e57f6392da62cdd8963496adef0d794e8f075
```

Рабочий журнал находится в `/tmp/osgard-remix-service-audit.json` в среде
проверки. Это журнал конкретного наблюдения, а не симуляция HTTP-ответов.
Дополнительно новый режим проверки здоровья выполнил ровно один `GET /health`
и получил `200 application/json`, `{"status":"ok"}`.

Перед записанным прогоном один запрос создания испытания был отправлен, но
вспомогательный скрипт завершился до сохранения ответа из-за ошибки обращения к
методу `urllib.request.Request`. Поэтому возможно существование ещё одного
приватного QA-испытания с неизвестным ID. Матч для него не создавался. Эта
неопределённость не скрывается и не считается успешным тестом идемпотентности.

## 2. Наблюдаемые маршруты

Все пути в таблице указаны относительно `/api/remix`.

| Метод и путь | Запрос | Полученный ответ |
| --- | --- | --- |
| `GET /health` | Без тела | `200 application/json`, `status: "ok"` |
| `POST /v1/challenges` | `creatorId`, `title`, `mode: "speed"`, целочисленный `seed`, `visibility: "private"` | `201 application/json`, объект испытания |
| `GET /v1/challenges` | Без тела | `405 text/plain`; список испытаний этим маршрутом не получен |
| `POST /v1/matches` | `challengeId`, `maxPlayers: 2` | `201 application/json`, объект матча |
| `GET /v1/matches/:id/state` | Без тела | `200 application/json`, фаза, число игроков, оставшееся время, счётчики и очки |
| `POST /v1/matches/:id/input` | `playerId`, `sequence`, `moveX`, `moveY`, `jump` | Принятая команда: `200 application/json`; повторный или меньший номер: `409 text/plain` |
| `GET /v1/matches/:id/result` | Без тела | До завершения: `409 text/plain`; в `RESULTS`: `200 application/json` |

Это перечень наблюдаемых маршрутов, а не полная спецификация неизвестного
исходного сервиса. Отдельный маршрут входа игрока не использовался: первая
принятая команда увеличила `players` с нуля до одного. Вместимость двух игроков
в ответе создания не является доказательством проверенного матча двух игроков.

### Объекты ответов

Схема ответа создания испытания, с заменёнными для краткости идентификаторами:

```json
{
  "id": "ch_example",
  "creatorId": "qa-remix-example",
  "title": "OSGARD QA 2026-10-17",
  "mode": "speed",
  "seed": 20261017,
  "rules": null,
  "objects": null,
  "visibility": "private",
  "playCount": 0,
  "remixCount": 0,
  "createdAt": "2026-10-17T09:51:47.266801977Z"
}
```

Ответ создания матча содержит `id`, `challengeId`, `maxPlayers` и `createdAt`.
В действительных ID матча присутствуют точки в метке времени. Клиент должен
принимать такие ID, одновременно исключая пути, параметры URL и сегменты `.`
или `..`.

Пример наблюдённого состояния после одной принятой команды:

```json
{
  "id": "match_example.1",
  "phase": "COUNTDOWN",
  "players": 1,
  "remainingMs": 1570,
  "replayFrames": 1,
  "scores": [{"playerId": "qa-remix-example", "score": 0.016666666666666666}]
}
```

Успешный ответ команды содержит `playerId`, трёхмерный массив `position`,
`velocityY`, `onGround`, `score` и `lastSequence`. После первой команды
`moveX: 1`, `moveY: 0`, `jump: false` получена позиция
`[0.08333333333333333, 0, 0]`. Это координаты сервиса, а не пиксели canvas.
Точка в консоли может показывать их ограниченную проекцию; она не должна
выдаваться за Unity-сцену или перемещаться как подтверждённая до ответа сервиса.

Результат содержит только следующие наблюдённые поля:

```json
{
  "matchId": "match_example.1",
  "phase": "RESULTS",
  "replayFrames": 2,
  "scores": [{"playerId": "qa-remix-example", "score": 0.03333333333333333}]
}
```

`replayKey`, полный журнал команд, подпись или хеш повтора в этом ответе
**отсутствовали**. Счётчик `replayFrames` сам по себе не подтверждает доступный
повтор, его целостность или сохранение после перезапуска сервиса. Полей `seed`
в наблюдённых состоянии и результате также нет: код из URL или локального
хранилища не становится подтверждённым свойством результата только от успешного
`GET /result`.

## 3. Последовательность команд и время

В собственном матче получена следующая последовательность:

| Команда | Ответ | Наблюдение |
| --- | --- | --- |
| Первый `sequence: 1` в `COUNTDOWN` | `200`, `lastSequence: 1` | Игрок добавлен, очки и `replayFrames` увеличились уже до `PLAYING` |
| Повтор `sequence: 1` | `409`, `stale input sequence` | Повтор отклонён |
| `sequence: 3` после принятого 1 | `200`, `lastSequence: 3` | Пропуск номера разрешён |
| `sequence: 2` после принятого 3 | `409`, `stale input sequence` | Меньший номер отклонён |

Следовательно, наблюдаемый контракт требует возрастающего номера, но не
непрерывной последовательности. Повтор не возвращает подтверждение исходной
команды. При потере её ответа клиент должен сохранить использованный номер и
не воспроизводить сомнительный `POST` автоматически. `GET /state` не возвращает
`lastSequence`, поэтому он не может сам по себе установить, была ли принята
потерянная команда данного игрока.

В начале `remainingMs` был равен 2540 в фазе `COUNTDOWN`. Следующий запрос после
паузы примерно до 23-й секунды жизни матча впервые вернул `PLAYING` и ровно
`remainingMs: 30000`. Последующие значения уменьшались, затем были получены
`RESULTS` и ноль. Такое наблюдение **совместимо с переходом фазы по обращению к
сервису**, при котором отсчёт игры начинается при обработке запроса. Это вывод
из HTTP-наблюдений; поведение таймера ещё не сверено с исходным кодом. Нельзя
обещать завершение через фиксированное число секунд после создания, пока этот
контракт не проверен.

## 4. Подтверждённый исторический дефект legacy-сервиса

Сначала сервис вернул `RESULTS`. Затем был получен итог, отправлена одна новая
команда того же QA-игрока и снова прочитан итог:

| Состояние | `replayFrames` | Очки QA-игрока |
| --- | ---: | ---: |
| Результат до позднего ввода | 2 | 0.03333333333333333 |
| Ответ позднего `sequence: 4` | Команда принята с `200` | 0.05 |
| Результат после позднего ввода | 3 | 0.05 |

Это не предположение о риске: завершённый результат изменился в проверенном
собственном матче. Для исправленного сервиса новая команда после `RESULTS`
должна отклоняться до изменения игрока, счёта и журнала; повторное чтение итога
должно возвращать те же зафиксированные данные.

Браузерная блокировка вне `PLAYING` уменьшает число случайных поздних команд.
Она не обеспечивает серверную защиту: сторонний клиент может обратиться к API
без кнопок этой страницы, а уже отправленная команда может прийти после границы
фазы. Поэтому прямой ответ legacy-сервиса следует описывать как полученное от
него значение на момент чтения. Новый guard фиксирует наблюдённый терминальный
снимок, но не превращает его в проверенный игровой повтор или доказательство
защищённой симуляции.

## 5. Непроверенные гарантии

- Синтетические запросы прошли **без заголовка авторизации**; `creatorId` и
  `playerId` задавались клиентом. Проверка не пыталась действовать от чужого
  игрока. Из её результатов нельзя вывести доказанную привязку ID к аккаунту
  или защищённое владение матчем.
- `visibility: "private"` принят и возвращён в объекте испытания. Проверка не
  доказывает механизм контроля доступа к этому испытанию.
- Матч и результат legacy-сервиса прочитаны в одном периоде его работы.
  Его контейнер не перезапускался, база не восстанавливалась. Долговечность
  активных матчей, последовательностей и испытаний после его перезапуска не
  установлена. Проверка рестарта нового guard относится только к уже
  зафиксированным терминальным снимкам в его отдельном томе.
- Идемпотентность создания испытания и матча не установлена. После потери
  ответа `POST` новая попытка может создать отдельную сущность.
- Не проверены полный повтор, защита от автоматизированного набора очков,
  одновременный матч двух игроков и связь этого API с Unity-процессом.

Эти ограничения должны сохраняться в отчёте о выпуске даже при зелёных тестах
браузерного восстановления или доставки WebAssembly.

## 6. Проверка, добавленная в репозиторий

`scripts/remix-service-contract-smoke.py` по умолчанию выполняет только один
запрос здоровья. Запись в сервис возможна исключительно с явным `--exercise`.

```sh
python scripts/remix-service-contract-smoke.py
python -m unittest discover -s tests -p test_remix_service_contract.py -v
```

Режим `--exercise` создаёт одно новое QA-испытание с `visibility: private` и
один матч. Он проверяет только их: схему ответов, отклонение команды во время
отсчёта, возрастающие номера, отсутствие преждевременного результата, отклонение
поздней команды и неизменность итога. Он не перечисляет чужие матчи и не пробует
неизвестные маршруты.

```sh
python scripts/remix-service-contract-smoke.py \
  --base https://osgard.world/api/remix \
  --exercise \
  --output /tmp/remix-contract-unique-run.json
```

Последняя команда выполняет реальные записи. Обычная проверка здоровья и
модульные тесты их не выполняют. Проверка после публикации явно вызывает
`--exercise` один раз для нового приватного QA-матча и сохраняет JSON-журнал
как артефакт выпуска. Повторно запускать её на неизменённом сервисе для
накопления одинаковых свидетельств не требуется.
Известное принятие поздней команды должно приводить к ошибке проверки, а не
считаться допустимым старым поведением.

Скрипт не повторяет `POST`, сохраняет намерение до сетевого запроса и отличает
неопределённый исход записи от подтверждённого отказа. При `--output` ответы
записываются атомарно в новый JSON-файл; существующий отчёт не перезаписывается.
Введены таймауты запросов и общий предел опроса. Если обратный отсчёт не удалось
проверить до его границы, результат этой проверки помечается как неустановленный
и общий прогон не объявляется успешным.

`tests/test_remix_service_contract.py` проверяет валидаторы, а не подменяет
настоящий сервис. В нём есть отклонение HTML вместо JSON, чужого ID матча,
нечисловых/бесконечных очков, повторяющихся игроков, некорректных идентификаторов
и именно наблюдённого изменения результата с двух кадров на три. Зелёные
модульные тесты этих валидаторов не означают исправления рабочего backend.

## 7. Граница доступа к исходному сервису и выбранный способ исправления

В текущем репозитории исходники отдельного Go-сервиса отсутствуют.
`docker-compose.production.yml` указывает `build: ../remix/backend`.
Разрешённая проверка метаданных на VPS нашла `/opt/remix/backend` и описала
**26 конкретных файлов** с SHA-256: `Dockerfile`, `go.mod`, точку входа
`cmd/api/main.go`, обработчики `internal/api/*.go`, доменную логику
`internal/domain/*.go` и связанные Go-тесты. Результат инвентаризации:
[GitHub Actions, запуск 39022809575](https://github.com/osmanosmanov6880-bot/osgard-world/actions/runs/39022809575).

Следующее действие — **выгрузить содержимое этих 26 файлов с VPS в артефакт
GitHub Actions для чтения и исправления** — было отклонено автоматической
проверкой разрешений. Указанная причина: перенос потенциально закрытого
серверного исходного кода за пределы VPS, для которого нужно явное разрешение
пользователя. Это отдельная граница доступа; разрешение на обычную публикацию
фронтенда через SSH не было принято автоматической проверкой как разрешение на
такую выгрузку.

Вывод исходников в логи, другой канал экспорта или обход этой блокировки не
выполнялись. Метаданные с именами файлов не заменяют просмотр их содержимого.
Вместо переноса закрытого кода написан оригинальный guard в этом репозитории.
Ему достаточно наблюдённого HTTP-контракта, он работает на том же VPS и не
получает доступа к файлам, секретам или внутренним данным Go-процесса.
Экспорт исходников не требуется для внедрения этой отдельной защиты API.

## 8. Контракт нового REMIX guard

Реализация: `server/remix_guard.py`, только стандартная библиотека Python.
Контейнер собирается из `server/RemixGuard.Dockerfile`. Предполагаемый путь
запроса: публичный Nginx → `remix-guard:8081` → `remix-api:8080`. Префикс
`/api/remix` снимает Nginx, как и до добавления guard.

Для каждого ID матча guard сериализует запросы одной из 256 постоянных
блокировок. Число блокировок не растёт с числом матчей. Для ввода проверяется
доступность записи SQLite, затем свежий `GET /state` с точным совпадением ID.
Только `PLAYING` или `RUNNING` с положительным `remainingMs` позволяет передать
один `POST /input`. Команда в `WAITING`, `COUNTDOWN` или при нулевом времени
получает `409 match_not_playing`, не достигая legacy-обработчика.

Как только ответ с однозначным ID сообщает `RESULTS`, в SQLite фиксируется
терминальная отметка. Она создаётся до полной проверки остальных полей, поэтому
ошибка очков, повторяющиеся неидентифицирующие JSON-поля или временная ошибка
`GET /result` не открывают ввод заново. Последующий ввод получает
`409 match_finished`, в том числе после рестарта guard и независимо от
доступности upstream. Неоднозначные ID/фаза и неразбираемый JSON не признаются
доказательством конкретного терминального матча; такой запрос завершается
ошибкой без пересылки команды.

Первый корректный терминальный `state` сохраняется и больше не заменяется.
Перед выдачей публичного `RESULTS` guard получает `result`, проверяет ID, фазу,
конечные числовые очки, уникальность игроков, количество кадров и соответствие
очков ранее наблюдённому состоянию. Затем оба объекта фиксируются одной
транзакцией SQLite. Только после подтверждённого commit возвращается `200`.
Выдаваемый JSON имеет отсортированные ключи и постоянную сериализацию.

Если результат временно недоступен, возвращается `503 terminal_result_pending`
без терминальных очков; безопасно повторить чтение. Ошибка схемы или
несовпадение состояния и результата даёт `503 upstream_contract`. Установленная
отметка продолжает запрещать ввод. Согласованный снимок не заменяется более
поздним upstream-ответом. Последующие `GET`/`HEAD` состояния и результата
обслуживаются из SQLite, даже когда исходный сервис недоступен.

Поддерживается первое обращение к уже существующему матчу: создавать его через
guard заранее не обязательно. Для ранее завершённого матча сохраняется первое
корректное терминальное состояние, увиденное **после включения guard**.
Изменения старого результата, произошедшие раньше, восстановить по этому
контракту невозможно.

Служебный `GET /health` проверяет реальную запись в SQLite и здоровье
legacy-сервиса. Готовность обозначается следующими полями:

```json
{
  "status": "ok",
  "service": "osgard-remix-guard",
  "schemaVersion": 1,
  "frozenResults": true,
  "storage": "ok",
  "upstream": "ok",
  "resultPolicy": "freeze-on-first-terminal-observation",
  "activeMatchRecovery": false,
  "replayVerification": false,
  "playerAuthentication": false
}
```

При недоступном upstream здоровье равно `503`, хотя уже замороженные результаты
остаются доступны из исправной SQLite. Ошибки открытия, записи или проверки
содержимого базы завершают запрос ошибкой; перехода к незащищённой пересылке нет.

### Сохранённые данные и границы гарантии

В базе находятся только терминальные DTO, ID матчей, служебные метки времени и
счётчик проверки записи. Заголовки авторизации, cookie, тела команд и запросов
создания не сохраняются. Логирование запросов, параметров и заголовков выключено.
Канонический путь не может выбрать другой upstream; прямые соединения не
используют proxy-переменные среды и не следуют перенаправлениям. Неоднозначные
пути и неподдерживаемые варианты маршрутов/методов матча не пересылаются.
Другие маршруты сохраняют тела, статусы и допустимые сквозные заголовки сервиса.
POST не повторяется автоматически; потеря ответа после отправки обозначается
`503 upstream_write_uncertain`.

Эта защита **не делает проверку фазы и изменение внутри старого Go-процесса
одной атомарной операцией**. Между подтверждённым `GET /state` и прибытием
`POST /input` фаза старого симулятора ещё может измениться. Уже отправленная
команда может завершиться позднее границы его часов. Guard сериализует такие
запросы относительно первого наблюдения терминальной фазы и замораживания;
он гарантирует неизменность публичного снимка после его фиксации, а не
переписывает таймер или физику неизвестного сервиса.

Один процесс guard должен владеть одним томом. Несколько одновременно
принимающих трафик экземпляров с общей базой не поддерживаются: SQLite
сериализует транзакции, но не общий интервал `GET → POST` между процессами.
Все публичные обращения к матчам должны идти через этот guard; прямой доступ
к исходному сервису остаётся за пределами его защиты. Сохранение активного
матча после рестарта upstream, владение игроком, идемпотентное создание и
криптографически проверенный повтор здесь не реализованы и не заявляются.

## 9. Запуск, хранение и изолированная проверка

Параметры контейнера согласованы с интеграцией:

```sh
python /app/remix_guard.py \
  --host 0.0.0.0 --port 8081 \
  --upstream http://remix-api:8080 \
  --database /var/lib/remix-guard/terminal.sqlite3
```

Именованный том `osgard-remix-guard-data` монтируется в `/var/lib/remix-guard`.
Каталог должен быть доступен UID/GID `10001`; база открывается с правами `0600`,
использует SQLite WAL и `synchronous=FULL`. Том требуется сохранять при замене
контейнера. Терминальные записи автоматически не удаляются. Заполненный или
недоступный для записи том блокирует новые команды; ёмкость и резервное
копирование тома входят в эксплуатацию сервиса. Удаление тома не является
поддерживаемым перезапуском и уничтожает сохранённые результаты.

Ввод ограничен 256 KiB, отдельный upstream-ответ — 1 MiB, одновременно
обрабатываются не более 32 соединений. Сетевой таймаут upstream по умолчанию
равен 3 секундам, бюджет последовательных обращений одного запроса — 10 секунд,
ожидание блокировки матча и SQLite — не более 2 секунд каждое. Запросы при
перегрузке получают ошибку, без повторной отправки POST. Для абсолютного
ограничения медленных upstream-заголовков используется таймер с прерыванием
сокета; он отменяется и завершается до освобождения рабочего потока.
Максимум 32 рабочих потока и 32 таймера укладывается в лимит контейнера
96 PID. Нулевое тело ответа и EOF ответа без `Content-Length` не обходят
проверку срока. Системный DNS resolver не прерывается этим таймером; адрес
upstream фиксирован. Если разрешение адреса или соединение вернулось после
истечения срока, POST после него не отправляется.

```sh
python -m unittest discover -s tests -p test_remix_guard.py -v
```

Финальный локальный прогон `test_remix*.py`: **37 тестов пройдены за 20,882
секунды** — 24 HTTP/SQLite-регрессии guard и 13 тестов контрактного валидатора.
Тесты guard поднимают
настоящие HTTP-серверы на loopback и временную SQLite. `Legacy` — явно
обозначенная модель наблюдённого дефекта: её ввод намеренно меняет очки даже
после `RESULTS`. Это оригинальная тестовая модель, а не полученный с VPS код.
Проверяются запрет COUNTDOWN/позднего ввода, соответствие ID, неоднозначные пути
и методы, повреждённые DTO, сериализация конкурирующего ввода и завершения,
неуспешный commit, абсолютный таймаут медленных заголовков с нулевым телом,
отклонение ложного успеха POST после прерванного EOF без `Content-Length`,
отсутствие повторного POST, сохранение терминальной отметки
при ошибке результата, первое чтение старого матча, байтовая неизменность после
рестарта при выключенном upstream и совместимость остальных ответов.

Для проверки настоящей цепочки Docker/Nginx предусмотрен отдельный стенд:

```sh
python scripts/remix-guard-fixture.py --host 0.0.0.0 --port 8080
```

Он использует `MATCH=match_existing.1`, `PLAYER=qa-guard-player`; контрольные
`POST /__fixture/countdown`, `/__fixture/playing`, `/__fixture/terminal`
устанавливают фазу. `GET /__fixture/echo?probe=a%2Bb&mode=test` возвращает
`{"path":"/__fixture/echo?probe=a%2Bb&mode=test"}`. Управляющие запросы нужны
только внутри изолированного контейнера стенда. `RemixGuard.Dockerfile` не
копирует ни этот скрипт, ни тестовые файлы в производственный образ.

Интеграционная проверка должна обращаться через настоящий Nginx с префиксом
`/api/remix`, фиксировать результат, пересоздавать guard с тем же томом,
выключать стенд upstream и сравнивать результат побайтово. После этого поздний
ввод остаётся `409`, а создание нового матча без upstream завершается `503`.
Этот стенд проверяет сетевую схему и долговечность guard. Отдельный свежий
собственный QA-матч после публикации подтверждает фактическое поведение
публичного API; результаты двух проверок не подменяют друг друга.
