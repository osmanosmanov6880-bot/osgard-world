# OSGARD CORE — Recovery Drill / испытание восстановления

**Состояние:** новый офлайн-инструмент проверки копии. Не является результатом испытания на production-сервере.

## Как безопасно проверить

1. Сначала сделайте согласованную копию через `bash scripts/backup-core-production.sh`. Не берите простым `cp` активный SQLite с WAL: результат может оказаться неполным.
2. Передайте **путь к уже готовому резервному файлу**, не к действующей Core-базе:
   ```bash
   python3 scripts/verify-core-backup.py /private/backups/core.sqlite3 --json
   python3 scripts/verify-core-backup.py /private/backups/core.sqlite3 --sha256 EXPECTED_64_HEX_DIGEST
   ```
3. Скрипт проверит SHA-256, сделает копию в отдельный приватный временный каталог, откроет только эту копию в read-only режиме и проверит `PRAGMA integrity_check`, наличие таблиц и версию схемы. В отчёт попадают только метаданные и хеш, без пользовательских записей. Любая ошибка возвращает ненулевой код.
4. Для реального плана восстановления дополнительно запустите копию Core на **изолированном хосте**, проверьте бизнес-операции и зафиксируйте измеренные RTO/RPO. Эта проверка **не** заменяет disaster-recovery учения и **не** доказательство корректной работы приложения на восстановленной БД.

### Локальные тесты и CI
```sh
python3 -m unittest discover -s tests -p test_core_backup_recovery.py -v
python3 -m py_compile scripts/verify-core-backup.py
```

Набор тестов создаёт только временные SQLite-файлы и проверяет валидную копию, совпадение SHA, некорректный SHA, повреждение, пустой файл, симлинк, посторонние данные и отсутствие таблиц. Никакая production-база не читается в CI.

### Ограничения безопасности
- **Никогда** не передавайте в репозиторий сами резервные файлы: они могут содержать хеши паролей, токены сессий и персональные данные. Не печатайте `sqlite_master.sql` или значения записей в общие логи.
- Источник открывается для копирования: используйте защищённый файл с ограниченными правами и заведомо доверенный путь. Исключите конкурентную подмену файла другим процессом.
- Рекомендована отдельная шифрованная offsite-копия, утверждённое расписание, срок хранения и алерты об устаревшей копии.
- Старый SSH-ключ, опубликованный в переписке, считать скомпрометированным и заменить по согласованной процедуре, **не** используя его в автоматических тестах.
- В реальном развёртывании необходимо отдельно проверить, что backup-job завершается успешно, копии доступны после потери VPS, а права доступа к архивам минимальны.

**Контракт:** этот инструмент не пишет в `server/`, `docker-compose.production.yml`, `nginx.conf`, production-базу, платёжные модули или API.
