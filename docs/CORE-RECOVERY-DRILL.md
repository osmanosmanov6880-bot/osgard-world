# OSGARD Core — backup, offline restore и локальное испытание HTTP

**Проверенный объём:** полный локальный цикл работающего Core → online SQLite backup → восстановление в новый каталог → новый процесс Core → проверка через HTTP. Данные для этого цикла создаются через обычные операции приложения в новой приватной базе. Production-база, Docker-хост, реальные пользователи и внешние сервисы в испытании не участвуют; production RTO/RPO не измерены.

## Три разных результата

| Команда | Что выполняет | Чего результат не подтверждает |
| --- | --- | --- |
| `scripts/verify-core-backup.py` | Копирует готовый standalone snapshot в приватный временный каталог; проверяет SHA-256, SQLite integrity/FK, по умолчанию Core schema и при наличии manifest его привязку | Запуск приложения и восстановление production |
| `scripts/restore-core-backup.py` | Проверяет связанный manifest и создаёт постоянную offline-копию в новом отдельном каталоге | Запуск сервиса, переключение трафика и production recovery |
| `scripts/core-recovery-drill.py` | Создаёт локальные данные через настоящий HTTP, снимает online backup и проверяет восстановленный сервер новым процессом | Пригодность конкретной production-копии, её доступность после потери хоста и достижение production RTO/RPO |

## 1. Создать согласованный backup

Для локального Core или на уже подготовленном сервере:

```sh
python3 server/core_backup.py backup \
  /private/live/core.sqlite3 \
  /private/backups/core-2026-10-17.sqlite3 --json
```

Для действующего production Compose используется `bash scripts/backup-core-production.sh`; запускать эту команду следует только на согласованном Docker-хосте. Подробности — [CORE-PRODUCTION.md](CORE-PRODUCTION.md).

SQLite online backup включает подтверждённые страницы WAL, а источник открывается с `mode=ro`: отсутствующий файл не создаётся. Снимок проверяется по `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, `user_version=1`, обязательным таблицам, столбцам и связям Core, включая журналы идемпотентности и Commerce. Эти таблицы существуют и при выключенных платежах; проверка их схемы не включает платёжный сервис. Дополнительные таблицы текущих модулей допускаются и входят в отпечаток схемы. Наличие версии `1` у произвольной чужой SQLite-базы недостаточно.

Успешная CLI-команда создаёт три новых файла с правами `0600`:

- `core-2026-10-17.sqlite3` — самостоятельный SQLite snapshot без WAL/SHM/journal;
- `core-2026-10-17.sqlite3.sha256` — контрольная сумма;
- `core-2026-10-17.sqlite3.manifest.json` — формат `osgard-core-backup/v1`, имя и размер файла, SHA-256 базы, время UTC, метод получения, версия/число таблиц и SHA-256 схемы, результаты integrity/FK.

Manifest публикуется последним. Существующие DB, checksum, manifest и destination-sidecar не заменяются. При обычной ошибке удаляются только созданные этой попыткой файлы. После аварийного завершения процесса или потери питания файлы без завершённого manifest нельзя считать опубликованной копией. Контрольные суммы нужно хранить вместе с резервным комплектом; для независимого контроля можно дополнительно передать ранее записанный доверенный SHA-256.

## 2. Проверить готовый snapshot

Передавайте готовую копию, не путь действующей базы:

```sh
python3 scripts/verify-core-backup.py \
  /private/backups/core-2026-10-17.sqlite3 \
  --manifest /private/backups/core-2026-10-17.sqlite3.manifest.json \
  --sha256 EXPECTED_64_HEX_DIGEST --json
```

Проверяется связка точных байтов DB, имени файла, размера, SHA-256 и схемы из manifest. На POSIX каждый родительский каталог источника открывается через directory descriptor и `O_NOFOLLOW`; симлинки, FIFO, устройства и пустые файлы отклоняются. SHA-256 рассчитывается из копируемых байтов, а идентичность и размер источника проверяются до/после копирования. SQLite открывает только временную копию в `mode=ro&immutable=1` с `query_only=ON`; исходный файл не используется как рабочая база. Любой обнаруженный `-wal`, `-shm` или `-journal`, в том числе пустой, отклоняется. Удалять sidecar ради прохождения проверки нельзя: сначала создайте корректный online backup.

Core schema теперь проверяется по умолчанию, включая старую копию без manifest. Флаг `--require-core` сохранён как явное указание того же профиля. Для произвольной SQLite нужен `--sqlite-only`: он устанавливает `validation_scope: "sqlite_only"`, `core_schema_checked: false`, `metadata_bound: false` и не подтверждает совместимость Core. `--sqlite-only` несовместим с `--require-core` и `--manifest`; противоречивые флаги дают ошибку. Python API сохраняет явный `drill(path, require_core=False)` для прежних диагностических потребителей; передача manifest всегда требует Core-проверку. Прежнему вызову без флагов для произвольной SQLite необходимо добавить диагностический режим.

Во всех режимах verifier сохраняет `service_started: false`, `application_restore_tested: false`, `application_restore_validated: false`, `rto_seconds: null`, `rpo_seconds: null`. `verification_seconds` измеряет только валидацию временной копии. JSON не содержит пользовательских строк, SQL-схемы, имён таблиц или секретов; ошибка даёт exit code `2`. Без независимо полученного `--sha256` совпадение файла с его копией/manifest не подтверждает происхождение резервного комплекта. `expected_sha256_verified` показывает именно наличие и успешную проверку такого аргумента; `metadata_bound` отдельно сообщает о привязке manifest.

Чтобы подготовить старый уже проверенный standalone snapshot к новому offline restore, команда `server/core_backup.py publish SOURCE NEW_DEST --sha256 TRUSTED_DIGEST --json` создаёт связанный комплект с методом `verified-offline-snapshot` и повторяет Core/integrity/FK-проверки.

## 3. Восстановить offline в новый каталог

Родитель `/private/restore-exercises` должен существовать, а `run-001` — отсутствовать:

```sh
python3 scripts/restore-core-backup.py \
  /private/backups/core-2026-10-17.sqlite3 \
  --manifest /private/backups/core-2026-10-17.sqlite3.manifest.json \
  --sha256 EXPECTED_64_HEX_DIGEST \
  --target-dir /private/restore-exercises/run-001 \
  --protected-root /private/custom-live-volume
```

Результат: приватный каталог `0700` с `core.sqlite3`, точной копией исходного `backup-manifest.json` и `restore-report.json`, все файлы `0600`. Отчёт содержит `status: "restored_offline"`, хеши DB и исходного manifest, результаты SQLite, `service_started: false`, `production_modified: false`. Начальный SHA относится к неизменённой offline-базе; после запуска приложения и новых записей он закономерно изменится.

Нельзя переиспользовать даже пустой каталог. Отклоняются симлинки во всех компонентах пути, `..`, имена с управляющими символами, стандартные production-каталоги `/var/lib/osgard-core` и `~/.osgard-core`, а также деревья `public`, `dist`, `PAGES` текущего комплекта. `--protected-root` добавляет известные оператору нестандартные live volumes. Инструмент не обнаруживает произвольные пользовательские схемы развёртывания; для них необходимо указать защищённые корни и выбрать отдельный доверенный родительский каталог.

CLI, входящий в архив Core, также поддерживает эту операцию:

```sh
python3 CORE/core_backup.py restore \
  /private/backups/core-2026-10-17.sqlite3 \
  /private/restore-exercises/run-002/core.sqlite3 \
  --manifest /private/backups/core-2026-10-17.sqlite3.manifest.json --json
```

`run-002` тоже должен быть новым. Из исходников путь скрипта — `server/core_backup.py`. Автоматического переноса этой базы в production volume, запуска production-сервиса или переключения трафика нет.

## 4. Полный локальный HTTP drill

Команда создаёт собственный новый набор данных и не принимает внешний API URL или существующую production-базу:

```sh
drill_parent="$(mktemp -d -t osgard-core-recovery-XXXXXXXX)"
python3 scripts/core-recovery-drill.py \
  --work-dir "$drill_parent/exercise" \
  --report "$drill_parent/report.json"
```

Нужен Python со стандартными модулями SQLite и возможность слушать `127.0.0.1` на случайном свободном порту. Docker, сторонние Python-пакеты, браузер, внешняя сеть и ключи не требуются. Скрипт последовательно запускает два отдельных процесса настоящего `server/core_server.py`. У каждого явно заданы локальная база, приватный web root, `--host 127.0.0.1 --port 0`; Commerce отключён, `--remix` не включается. Переменные платёжных/облачных провайдеров и `PYTHONPATH` родителя не передаются.

В ходе выполнения проверяются:

1. Регистрация трёх локальных аккаунтов, создание проекта, изменение условий, принятие контракта, запись тестового расхода, реальный HTML artifact, членство viewer и выполненная настоящим worker задача — через HTTP.
2. Удерживаемое read-only соединение оставляет подтверждённые записи в WAL: основной файл показывает ноль проектов, HTTP — один. Попытка offline-копирования такого файла должна завершиться отказом; online backup обязан содержать проект.
3. Работающий источник принимает ещё одну запись после снимка. Восстановление возвращает сохранённую ревизию и исключает более позднее изменение.
4. Новый процесс на восстановленной базе принимает прежнюю сессию и правильный пароль. Проект, ревизии, события, HTML assets, задачи и членство совпадают со snapshot.
5. Viewer читает проект и artifact, но не может менять проект; посторонний аккаунт и аноним не получают доступ. Хеш HTML совпадает с содержимым, assets/jobs ссылаются на существующие сохранённые ревизии.
6. Повтор исходного запроса с тем же idempotency key не добавляет второй расход. Новая запись в восстановленную ветку сохраняется после завершения процесса.
7. Финальные integrity/FK проходят. Восстановленные действия не меняют остановленную исходную базу, резервный DB и manifest.

Выполненный локальный цикл 17 октября 2026 года наблюдал 3 пользователей, 1 проект, 1 участника, 6 сохранённых ревизий, 1 HTML asset, 1 completed job и 1 запись расхода. Ревизия снимка — 6, более поздняя ревизия исходника — 7. Это созданные для проверки локальные данные: расход является самостоятельно записанным тестовым значением, не платёжной транзакцией; подтверждённая выручка остаётся нулевой. В JSON явно указаны `production_backup_used: false`, `production_restore_tested: false` и `production_rto_rpo_measured: false`. Продолжительность шагов описывает только этот локальный запуск.

### CI и сохранение результата

```sh
python3 scripts/core-recovery-drill.py \
  --work-dir "$RUNNER_TEMP/osgard-core-recovery" \
  --report "$RUNNER_TEMP/core-recovery-report.json"
```

Загружайте как artifact только `$RUNNER_TEMP/core-recovery-report.json`. В рабочем каталоге также есть `report.json`, но весь каталог содержит DB с хешами паролей и сессий, поэтому его нельзя публиковать. JSON содержит итоги, количества, хеши и длительности без пользовательских записей и учётных данных.

При обычной runtime-ошибке возвращается exit code `2`, `status: "failed"`, текст нарушенной проверки и список только уже завершённых проверок. Новый внешний путь `--report` сохраняет такой отчёт и при отказе из-за уже существующего work-dir; старый work-dir не изменяется. Если сам путь `--report` недопустим, занят или недоступен для записи, команда завершается до старта без перезаписи чужого отчёта. Для повторного запуска выбирайте новый каталог и новый путь отчёта.

Регрессии:

```sh
python3 -m unittest discover -s tests -p test_core_backup_recovery.py -v
python3 -m unittest discover -s tests -p test_backup_shell_contract.py -v
python3 -m unittest discover -s tests -p test_core_recovery_http.py -v
python3 -m unittest discover -s tests -p test_core_restored_operations.py -v
```

Shell suite эмулирует только Docker transport и расположение container-файлов, выполняя настоящий встроенный Python/online-backup/publish на локальном CoreStore. Он проверяет также недостающий источник, неправильную схему, FK orphan, повреждение переноса и коллизии DB/manifest/checksum/sidecar. Это не исполнение production Docker-хоста. HTTP suite выполняет настоящий локальный цикл и проверяет изоляцию окружения, отчёт при ошибке и запрет перезаписи.

Пакетная команда для всех `test_core_*` — `npm run qa:core-recovery-tests`. Полный HTTP drill запускается отдельно и требует новый work-dir:

```sh
npm run qa:core-recovery -- \
  --work-dir "$RUNNER_TEMP/osgard-core-recovery" \
  --report "$RUNNER_TEMP/core-recovery-report.json"
```

Это альтернативная запись прямой Python-команды, а не второй запуск в тот же каталог. Shell suite `test_backup_shell_contract.py` остаётся отдельной проверкой.

## 5. Восстановленные незавершённые операции

`test_core_restored_operations.py` сохраняет регрессии восстановления операций из PR #129. Он использует настоящие `Store`, SQLite backup API, verifier и повторное открытие SQLite. Платёжная граница заменена локальным `FakeProvider`; конструирование реального SDK-провайдера принудительно блокируется. Учётные записи и ответы провайдера синтетические. Внешних аккаунтов, сетевых запросов и денежных операций в этом наборе нет; он дополняет отдельный реальный HTTP drill.

| Сбой | Что проверяет восстановление |
| --- | --- |
| Checkout создан провайдером, ответ потерян | Повтор после backup/restore использует прежний durable provider key; создаётся одна сессия |
| Refund создан провайдером, ответ потерян | После restore остаётся один возврат; повтор webhook не меняет учёт второй раз |
| Истёк допустимый интервал неизвестного Checkout/Refund | После restore возвращается `reconciliation_required`; новая операция не создаётся |
| Потерян ответ сборки или внутреннего выпуска | Повтор сохранённого ключа после restore возвращает прежний artifact/release; количество остаётся 1 |
| Запрошена внешняя публикация | Core отклоняет неподдерживаемое действие и после restore; внешний publisher этим тестом не проверен |

Текущий Commerce ограничивает повтор неизвестного результата через `RETRY_WINDOW` и требует сверки просроченных операций. Сохранённый ключ нельзя считать бессрочной гарантией внешнего провайдера.

## План восстановления реальной копии

1. Зафиксировать момент сбоя, версию приложения, время последней надёжной копии и ожидаемый хеш. Получить копию из независимого хранилища и проверить её verifier с Core-профилем.
2. Восстановить в новый каталог на отдельном изолированном хосте. Оставить новые платежи и внешние публикации выключенными; защитить исходный snapshot от изменений.
3. Проверить вход/права, проекты, версии, файлы, обучение, выдачу доступа и аудит. Повторять незавершённый запрос из сохранённого журнала только с исходным ключом.
4. Сверить события провайдера и publisher после времени snapshot до включения новых операций. Snapshot, снятый до внешнего списания или публикации, может не содержать его ключа: локальный restore сам по себе не предотвращает повтор. Неизвестные результаты требуют сверки.
5. Измерить RTO от начала восстановления до успешных обязательных пользовательских сценариев; RPO — фактический интервал потерянных подтверждённых данных. Длительность `integrity_check` или локального drill не равна production RTO.
6. После сверки выполнить отдельно согласованное переключение трафика с возможностью отката. Сохранить операторский отчёт, список проверок и измеренные RTO/RPO в закрытом хранилище.

## Ограничения и эксплуатация

- Для backup/restore установлен предел 1 GiB на SQLite-файл. Online backup проверяет логический `page_count × page_size`, включая WAL, до копирования и повторяет лимит во время progress. SQL/online copy имеют бюджет 30 секунд; manifest ограничен 64 KiB. Эти пределы нужно учитывать до роста production-данных; они не являются измеренной ёмкостью сервиса.
- SHA-256 и manifest обнаруживают повреждение или несвязанные файлы; manifest не подписан. В отчёте стоит `metadata_authenticated: false`. Подмена одновременно DB и всех её метаданных требует отдельной защиты хранилища или независимо сохранённого доверенного digest.
- Пути и их родительские каталоги должны быть доверенными и закрытыми для конкурентной подмены. Проверки симлинков и исключительное создание не заменяют изоляцию от враждебного процесса с тем же UID и правом менять родительские каталоги.
- Копии могут содержать личные данные, хеши паролей, активных сессий и резервных кодов. Не помещайте их в Git, публичный ZIP, PAGES, web root или общедоступный artifact. Храните согласованную шифрованную offsite-копию, расписание и срок хранения; проверяйте возраст последнего успешного снимка и свободное место.
- Перед доверием к production recovery отдельно испытайте резервирование на целевом Docker-хосте, получение копии после потери VPS, изолированный запуск разрешённой реальной копии, нужные бизнес-связи и план ручного переключения. Для этого нужен конкретный backup и согласованный доступ; локальный drill такие результаты не заявляет.
