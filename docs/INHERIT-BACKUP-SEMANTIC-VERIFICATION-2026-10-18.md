# OSGARD CORE / INHERIT — проверка семантики резервной копии

**18 октября 2026 года** · Изменение процедуры проверки восстановленного снимка SQLite.

## Что было не проверено

Стандартные `PRAGMA integrity_check` и `foreign_key_check` обнаруживают
повреждение страниц SQLite и нарушенные внешние ключи. Они не могут определить,
что JSON текущего мира отличается от последнего сохранённого поколения или что
цепочка `delta → snapshot → hash` нарушена при сохранении корректного
синтаксиса базы.

Проверка копии могла успешно завершиться, а Core затем отклонял бы чтение
повреждённого мира с HTTP 503. Предположения о том, что успешный
`integrity_check` гарантирует игровую восстанавливаемость, были неправильными.

## Новая обязательная проверка для Core-снимка

`scripts/verify-core-backup.py` по-прежнему:

1. Без перехода по символическим ссылкам копирует согласованный одиночный файл
   в отдельный каталог с приватными правами. Исходный файл не открывается на запись.
2. Сверяет байты, SHA-256 при наличии доверенного ожидаемого значения, SQLite
   integrity и foreign keys.
3. Проверяет ожидаемые таблицы и ключевые столбцы Core, а при наличии любой
   таблицы INHERIT — весь набор таблиц и SQL-триггеры неизменяемости.

Теперь для каждого доступного в снимке мира INHERIT дополнительно вызывается
**тот же** `core_inherit.verify_lineage`, который применяет рабочий API.
Проверка ограничена действующими лимитами пилота (до 128 поколений на мир,
до 1 024 следов и 100 в одном поколении) и включает:

- базовые объекты и их хэш, идентичность шаблона и происхождение;
- непрерывную нумерацию поколений, связку parentHash, delta, снимок и его хэш;
- соответствие текущих объектов, номера поколения и итогового хэша всей
  подтверждённой цепочке.

При ошибке **вся проверка восстановления завершится отказом** без исправления
данных. Название и ID мира, содержимое и авторы не включаются в сообщение об ошибке.
Серверный код не изменяет ни исходную копию, ни приватный тестовый файл.

## Пример запуска (только для уже согласованного резервного снимка)

```bash
python3 scripts/verify-core-backup.py /secure/backups/core-snapshot.sqlite3 --sha256 TRUSTED_EXPECTED_SHA256 --json
```

Заменить заглушку `TRUSTED_EXPECTED_SHA256` на доверенный внешний хэш.
Файл должен быть завершённой SQLite-копией без незакрытых `-wal/-shm/-journal`.
Не запускайте эту команду на активно изменяемой базе вместо процедуры backup.

В JSON теперь есть:

| Поле | Смысл |
|---|---|
| `core_schema_checked` | Проверена схема Core |
| `inherit_lineage_checked` | Проверены внутренние записи INHERIT |
| `inherit_worlds_checked` | Количество проверенных миров (без идентификаторов) |
| `inherit_generations_checked` | Количество проверенных записей поколений |
| `production_modified` | Всегда `false` для этой проверки |
| `application_restore_validated` | Остаётся `false`: рабочий рестарт приложения не проверяется |

Если копия создана до появления INHERIT и новых таблиц нет,
`inherit_lineage_checked=false`, счётчики 0. Это не ошибка при совместимом
старом Core-снимке. При `--sqlite-only` всегда проверяется **только**
структурная корректность SQLite; семантическая проверка Core/INHERIT намеренно
**отключена**, такой результат нельзя считать подтверждением восстановления игры.

## Границы доказательств

Успешная проверка доказывает внутреннюю согласованность скопированных данных
по действующему коду. Она не является криптографической подписью независимой
стороны, не выявляет согласованное переписывание всей истории владельцем
SQLite-файла и не проверяет реальные RTO/RPO, восстановление всей VPS,
действительность аккаунтов, Unity или старый активный движок REMIX.

Тесты `tests/test_core_inherit_backup_semantics.py` отдельно создают
нормальные и испорченные приватные копии: неверный baseline, повреждённый JSON,
исправный JSON с искажённым tip, чужой хэш, неправильное поколение, изменение
дельты при восстановленном SQL-триггере и повреждение одного из двух миров.
Сравниваются SHA-256 до и после отказа. Выполнение входит в
`npm run qa:core-recovery` через обязательное обнаружение `test_core_*.py`.
